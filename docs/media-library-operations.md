# 媒体文件库上线与运行手册

本手册用于决定新媒体文件库是否具备冻结旧应用的条件。它不授权删除旧代码、归档旧数据或切换生产入口。

## 1. 验收前保护数据

- 先备份数据库、待入库目录、正式文件目录和工作目录。
- 首次验收只使用真实媒体的副本，不直接使用唯一原件。
- 确认 FFmpeg 与 FFprobe 可从命令行运行，并记录版本。

## 2. 配置目录

配置 API 的待入库、正式库、工作目录和数据库路径。待入库、正式库和工作目录必须互不相同、互不包含，数据库不能放在待入库目录中。确认服务账号对四个位置具有所需权限，并在设置页检查“目录可写”“FFmpeg 可用”“FFprobe 可用”。

不要把仓库根目录、用户主目录、旧应用数据目录或 `apps/media-web/.e2e-data` 当作真实运行目录。

## 3. 启动顺序

1. 在 `apps/media-api` 安装依赖并执行 `alembic upgrade head`。
2. 启动 API，确认 `/health` 返回正常状态。
3. 设置 Web 的 `VITE_API_BASE_URL` 后启动 `apps/media-web`。
4. 打开设置页核对四个路径、扫描间隔、自动扫描开关和处理器开关。

## 4. 上线验收清单

- [ ] 图片：刷新后出现，能够填写多位作者、一个系列和多个标签，入库后源文件移走且显示名称可检索。
- [ ] 普通视频：无需前置处理即可完成同样流程，并能正常预览和检索。
- [ ] MP4/M4A：同名文件被一个注册处理器合并，只产生一个正式 MP4，两个原始源文件都被清理。
- [ ] 同名冲突—跳过：对话框显示双方预览，跳过后待入库源文件仍保留。
- [ ] 同名冲突—两者都保留：新文件使用 `(2)` 后缀，原文件不变，两份资料都可读取。
- [ ] 同名冲突—替换：先选择替换、再确认不可撤销提示；最终只保留一个正式资产并使用新文件及新资料。
- [ ] 失败隔离：构造一个无效处理输入，只有对应卡片失败，其他图片仍能入库。
- [ ] 重启恢复：在处理排队或可恢复入库操作存在时重启 API；恢复期间禁止新入库，完成后文件、数据库和界面状态一致。
- [ ] 文件库搜索：按显示名称、实际文件名、作者、系列、标签和媒体类型分别检索。
- [ ] 自动与手动扫描：两种方式都能发现稳定文件；临时下载后缀不会被入库。

自动发布门执行：

```powershell
python -m pytest apps/media-api/tests -q
npm --prefix apps/media-web test
npm --prefix apps/media-web run build
npm --prefix apps/media-web run e2e
```

四条命令必须全部通过；FFmpeg 相关测试不得跳过。

## 5. 旧应用保护

分别启动并检查 `apps/api`、`apps/desktop`、`apps/feishu`、`apps/telegram` 和 `apps/web`，确认本次媒体库改造没有修改其入口、配置或数据。验收记录中要保留启动结果和任何已知的原有问题。

## 6. 冻结条件

只有目录检查、人工清单和自动发布门全部通过后，才可以提出冻结旧应用的决定。任一项失败时继续保留旧入口，不用新系统覆盖唯一数据，并先修复和重新验收。

## 7. 后续切换

删除旧代码、清理归档、迁移真实数据和切换默认入口必须使用另一份经过评审的设计与实施计划，并放在单独提交中完成。本阶段不得执行这些操作。
