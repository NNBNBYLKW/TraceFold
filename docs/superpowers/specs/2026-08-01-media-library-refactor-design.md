# TraceFold 媒体文件库重构设计

- 日期：2026-08-01
- 状态：设计已确认
- 重构策略：在仓库内平行建设新应用，验收后再单独处理旧系统退场

## 1. 背景与判断

TraceFold 当前实现已经偏离“方便管理下载文件”的初衷。现有前端把路由、状态、事件、渲染和国际化集中在超大入口文件中；后端围绕 Capture、Pending、Workbench、Dashboard、Knowledge、AI 等概念形成交叉依赖；事务边界和提交行为散落在多个模块；测试同时存在静态字符串断言、运行目录假设冲突和归档文档引用等问题。

继续在现有结构中局部修补，会让新的媒体入库流程继续依赖旧领域模型。因此本次不在旧应用上演进，而是在同一仓库内建立独立的新媒体文件库应用。旧应用在新系统验收前保持不动，旧代码的删除或归档作为后续独立工作处理。

## 2. 产品目标

软件只解决本地媒体文件从“下载完成”到“可检索文件库”的过程：

1. 用户将下载的视频或图片放入指定待入库目录。
2. 软件自动扫描，或由用户手动刷新。
3. 软件识别是否需要前置处理；首个处理器负责合并同名 MP4 与 M4A。
4. 用户预览文件并手动填写作者、系列和内容标签。
5. 用户执行正式入库，文件移动到正式文件夹。
6. 入库完成后可通过显示名称、作者、系列、标签和媒体类型查找文件。

产品体验目标是让普通文件的日常流程保持为：

> 刷新 → 选择 → 标注 → 正式入库

前置处理、事务恢复和清理属于后台能力，不额外暴露为复杂的任务管理流程。

## 3. 明确范围

### 3.1 首版包含

- 图片和视频使用相同的元数据模型。
- 一个媒体可以有多位作者。
- 一个媒体最多属于一个系列，也可以不属于任何系列。
- 一个媒体可以有多个内容标签。
- 物理文件默认保持原名称。
- 用户可以设置独立的显示名称；显示名称只存入数据库，不修改物理文件名。
- 普通媒体可直接入库。
- 同名 MP4 与 M4A 可以自动合并为一个 MP4 后入库。
- 前置处理采用注册表和流水线设计，后续可以增加新处理器。
- 文件名或内容冲突采用 Windows 式弹窗，由用户查看预览后选择。
- 正式文件库提供图库浏览、搜索和元数据筛选。

### 3.2 首版不包含

- 旧系统业务数据迁移。
- 下载器、浏览器抓取和网络资源管理。
- AI 自动标签、内容识别和推荐。
- 多用户、权限、远程部署和云同步。
- 一个媒体同时属于多个系列。
- 通过资料编辑操作修改物理文件名。
- Capture、Knowledge、Workbench、聊天机器人等旧系统领域。
- 按作者或系列创建物理子目录。首版文件直接存放在正式文件夹根目录，由数据库元数据负责组织。

## 4. 总体架构

新系统由两个平行应用组成：

```text
apps/
  media-api/
    src/
      api/
      intake/
      processing/
      catalog/
      taxonomy/
      storage/
      infrastructure/
  media-web/
    src/
      inbox/
      library/
      conflicts/
      settings/
      shared/
```

### 4.1 `media-api`

新的 FastAPI 应用，使用独立 SQLite 数据库。内部按职责拆分：

- `api`：HTTP 请求、响应模型、错误转换和 SSE 事件流。
- `intake`：扫描待入库目录、识别候选文件、管理待入库状态。
- `processing`：处理器注册、计划生成、任务执行、结果验证。
- `catalog`：正式媒体资产、查询和元数据修改。
- `taxonomy`：作者、系列和标签。
- `storage`：所有目录、移动、暂存、删除、预览图和冲突命名操作。
- `infrastructure`：SQLite、迁移、事务、任务执行器、日志和启动恢复。

模块之间通过应用服务和明确的数据结构通信，禁止跨模块直接操作对方的数据表。只有 `storage` 可以改变文件系统；处理器只能在工作目录内读取输入并产生输出，不能删除源文件或直接移动到正式目录。

### 4.2 `media-web`

新前端只包含四个产品模块：

- `inbox`：待入库图库、状态、预览、选择、标注和入库动作。
- `library`：正式文件库浏览、筛选、搜索和资料编辑。
- `conflicts`：冲突预览和解决选择，以弹窗形式出现。
- `settings`：目录、自动扫描和处理器开关。
- `shared`：媒体预览、标签选择器、错误提示和通用 API 客户端。

页面不能直接理解文件路径、执行文件操作或自行推进状态机。它只提交用户命令，并依据 API 返回的 `status` 和 `allowed_actions` 显示可用操作。

### 4.3 运行配置

新系统至少需要以下独立配置：

- `INBOX_DIR`：待入库目录。
- `LIBRARY_DIR`：正式文件目录。
- `WORK_DIR`：处理暂存、事务暂存、临时备份和可再生预览图目录。
- `DATABASE_PATH`：新媒体库 SQLite 文件。
- 自动扫描间隔。
- 各处理器的启用状态和是否允许自动执行。

启动时必须验证三个文件目录不是同一路径，也不存在会导致递归扫描的父子包含关系。数据库与工作目录不能放在待入库目录内。

## 5. 数据模型

### 5.1 核心实体

#### `InboxItem`

表示一次待入库工作单元，而不是单个物理文件。普通图片或视频通常关联一个 `SourceFile`；MP4 与 M4A 配对后关联两个源文件。

主要字段包括：标识、媒体类型、发现时间、当前状态、建议实际文件名、错误信息、处理计划版本、创建和更新时间。

#### `SourceFile`

记录待入库源文件的规范路径、扩展名、大小、修改时间、扫描指纹、是否为主要媒体、是否仍然存在，以及所属 `InboxItem`。

#### `ProcessingPlan`

记录分析器针对一个 `InboxItem` 生成的有序处理步骤、处理器版本、输入和预期输出。计划必须持久化，使应用重启后可以解释和恢复未完成任务。

#### `ProcessingJob`

记录一次处理计划执行，包括状态、尝试次数、开始和结束时间、当前步骤、输出位置、诊断信息和可重试性。

#### `MediaAsset`

表示正式入库后的逻辑媒体。主要字段包括：媒体类型、实际文件名、正式相对路径、可选显示名称、大小、内容哈希、创建时间、入库时间和预览信息。

#### `Author`、`Series`、`Tag`

三个独立词表实体。名称按去除首尾空白后的标准值进行唯一性校验，同时保留用户输入的展示形式。

### 5.2 关系约束

- `InboxItem` 与 `SourceFile`：一对多。
- `InboxItem` 与 `ProcessingJob`：一对多。
- `MediaAsset` 与 `Author`：多对多。
- `MediaAsset` 与 `Tag`：多对多。
- `MediaAsset` 与 `Series`：可选多对一，即每个媒体最多一个系列。

图片和视频不使用两套表。它们共享 `MediaAsset`，通过 `media_type` 区分；类型特有信息放在受控的媒体详情字段中，不复制作者、系列和标签关系。

### 5.3 名称语义

- `actual_filename`：正式目录中的真实文件名，入库后资料编辑接口只读。
- `display_name`：可选用户名称，可以随时编辑。
- 界面优先显示 `display_name`；为空时回退到 `actual_filename`。
- MP4 与 M4A 合并后，结果沿用 MP4 的基本文件名和 `.mp4` 扩展名。

## 6. 待入库状态机

`InboxItem` 使用以下状态：

```text
discovered
  → analyzing
  → processing
  → ready_to_tag
  → conflict
  → ingesting
  → completed

任意分析、处理或入库阶段 → failed
failed → analyzing | processing | ready_to_tag
conflict → ready_to_tag | ingesting
```

状态变化只能由后端应用服务执行，并在同一数据库事务中记录状态事件。API 返回当前状态和允许的下一步动作，避免前后端分别维护一套规则。

`completed` 项不再出现在默认待入库列表中，但保留最小操作历史用于诊断。源文件消失不自动等同于完成；系统必须根据操作日志判断是用户删除、外部移动还是入库流程中的预期清理。

## 7. 扫描与发现

扫描器同时支持定时扫描和手动触发，两者调用同一个幂等应用服务。

### 7.1 文件稳定性

- 忽略 `.part`、`.crdownload` 等明确的下载临时文件。
- 根据规范路径、大小和修改时间记录候选文件。
- 文件至少连续两次观察保持大小和修改时间不变，才进入正式分析。
- 尚未稳定的文件可以在界面显示为“等待下载完成”，但不能开始处理或入库。

### 7.2 幂等与配对

- 同一路径、大小和修改时间组合不会重复创建 `InboxItem`。
- 分析器以目录、基础文件名和受支持扩展名识别 MP4 与 M4A 配对。
- 配对规则属于处理器的检测逻辑，不写死在扫描器中。
- 扫描阶段使用轻量指纹；正式入库准备阶段计算完整内容哈希。

## 8. 可扩展前置处理

处理系统由注册表、计划器和执行器组成：

```text
检测是否适用
  → 生成有序处理计划
  → 在 WORK_DIR 中执行
  → 验证输出
  → 将有效输出交给入库流程
```

每个处理器必须声明：唯一名称、版本、支持的输入、适用性检测、是否默认自动运行、资源要求、执行步骤、输出验证和错误分类。

系统发现文件后，由所有已启用处理器参与分析。只有声明为安全自动执行、且配置允许自动执行的处理器才会自动启动；其他处理器只生成建议计划，用户可以手动执行。多个处理器适用时，由计划器依据显式优先级和依赖关系组成流水线，而不是在业务代码中编写扩展名分支。

首个 `mp4_m4a_merge` 处理器：

- 检测同一目录下同基本名称的 `.mp4` 和 `.m4a`。
- 在工作目录生成合并后的临时 MP4。
- 使用媒体探测验证输出同时包含可用视频流和音频流。
- 不覆盖或删除输入文件。
- 只有验证后的输出才能成为入库候选。

处理失败只影响当前 `InboxItem`。任务保存结构化错误、可重试标记和简短用户提示，其他文件可以继续扫描、标注和入库。

任务由单进程内的持久化执行器处理。任务记录存储在 SQLite 中，应用启动时恢复排队或中断任务。首版不引入 Redis、Celery、独立任务服务或 WebSocket。

## 9. 标注规则

待入库元数据作为 `InboxItem` 的草稿保存，用户可以在处理完成前预先填写，但只有输出有效且状态允许时才能正式入库。

- 作者：零到多位；入库前允许为空。
- 系列：零或一项。
- 内容标签：零到多项。
- 显示名称：可选。

首版不强制要求至少一个作者或标签，以免把简单文件入库变成表单审批。界面允许对多个待入库项目批量追加作者或标签；系列批量操作会替换每个选中项目当前的单一系列，并明确提示这一行为。

## 10. 正式入库事务

入库使用持久化 `IngestOperation` 操作日志，分为准备、提交和清理三个阶段。

### 10.1 Prepare

1. 验证源文件或处理输出仍然存在且未发生变化。
2. 验证草稿元数据和关系约束。
3. 计算最终输入的完整内容哈希。
4. 计算目标实际文件名并检测名称和内容冲突。
5. 检查正式目录可用空间，并将输入复制到 `LIBRARY_DIR/.staging/<operation-id>`；源文件在提交完成前始终保留。
6. 验证暂存文件大小、哈希和可读性。
7. 持久化操作日志、暂存位置和后续动作。

### 10.2 Commit

1. 将暂存文件原子移动到正式目标位置。
2. 在同一个 SQLite 事务中创建或替换 `MediaAsset`、写入作者/系列/标签关系、把 `InboxItem` 标记为 `completed`，并把 `IngestOperation` 标记为已提交。

如果文件移动成功而数据库提交失败，启动恢复会根据操作日志重新完成数据库提交或将文件安全退回暂存区。任何恢复动作都必须先校验哈希，不能凭文件名猜测。

### 10.3 Cleanup

只有 Commit 完成并验证后，统一清理服务才可以删除：

- 普通入库的待入库源文件。
- MP4 与 M4A 合并场景中的原始 MP4、原始 M4A。
- 工作目录中的处理输出、事务暂存和临时替换备份。

处理器本身无权删除源文件。清理失败不会回滚已经成功的入库，而是记录可重试警告；后续启动或后台清理任务继续处理。

## 11. 冲突处理

在 Prepare 阶段检测以下冲突：

- 最终目标存在同名文件。
- 正式文件库中存在相同内容哈希。
- 名称冲突和内容冲突同时发生。

系统弹出 Windows 式对比窗口，展示库内文件和待入库文件的预览图、实际文件名、大小、时间、媒体信息和已有元数据。即使内容哈希完全相同，也由用户决定，不自动删除待入库文件。

用户可选择：

- **跳过**：结束本次入库尝试，源文件保留在待入库目录，项目回到可处理状态。
- **两者都保留**：使用下一个可用的 `name (2).ext`、`name (3).ext` 等实际文件名；显示名称不自动追加后缀。
- **替换**：将库内旧文件移到本次操作的临时备份区，提交新文件和本次待入库元数据；库内只保留一个逻辑资产，并沿用原 `MediaAsset` 标识以保持引用稳定。提交验证成功后再由 Cleanup 删除临时备份。恢复逻辑在异常时可以还原旧文件和旧元数据。

冲突选择与哈希、目标名称一起记录。源文件发生变化后，旧选择失效并重新提示。

## 12. API 边界

API 按用户意图设计，不暴露通用数据库 CRUD 或任意文件操作。

```text
POST  /api/inbox/scan
GET   /api/inbox/items
GET   /api/inbox/items/{id}
PATCH /api/inbox/items/{id}/metadata
POST  /api/inbox/items/{id}/process
POST  /api/inbox/items/{id}/ingest

POST  /api/conflicts/{id}/resolve

GET   /api/library/assets
GET   /api/library/assets/{id}
PATCH /api/library/assets/{id}/metadata
POST  /api/library/assets/{id}/reveal

GET/POST/PATCH /api/authors
GET/POST/PATCH /api/series
GET/POST/PATCH /api/tags

GET   /api/events
```

命令接口支持请求幂等标识，重复点击或网络重试不能创建重复任务或重复资产。`GET /api/events` 使用 SSE 推送扫描、处理和入库状态变化；断开 SSE 不影响功能，客户端重新获取列表即可恢复一致状态。

媒体预览通过受控的媒体标识接口提供，不让浏览器接收可写物理路径。资料修改接口只能更新显示名称和分类关系，不能修改正式相对路径、实际文件名或内容哈希。`reveal` 只允许让本机文件管理器定位已经登记的正式资产，不接收任意客户端路径。

## 13. 用户界面

已确认采用“图库 + 右侧抽屉”布局。

### 13.1 待入库

- 顶部只保留搜索、状态筛选、媒体类型筛选、手动刷新和自动扫描状态。
- 卡片直接显示待标注、处理中、冲突和失败等状态，不设置独立任务中心。
- 选中卡片后，右侧抽屉展示预览、只读实际文件名、可选显示名称、作者、系列和内容标签。
- 普通项目的主操作是“正式入库”；处理中的项目显示进度；失败项目允许查看原因和重试。
- 多选用于批量追加作者或标签，不能绕过每个项目的状态约束。

### 13.2 正式文件库

- 继续使用图库布局。
- 支持按显示名称或实际文件名搜索。
- 支持按作者、系列、标签和媒体类型组合筛选。
- 详情中可以修改显示名称和分类关系，但不能重命名物理文件。
- 主操作是预览、打开所在目录和编辑资料。

### 13.3 冲突弹窗

冲突不是常驻工作区。只有用户发起入库且 Prepare 检测到冲突时，才展示左右对比预览和“跳过、两者都保留、替换”选择。

## 14. 错误处理与可观察性

- 用户错误返回稳定错误代码和可执行提示，例如“文件仍在下载”“源文件已变化”“目标目录不可写”。
- 处理器错误区分可重试、输入无效和系统错误。
- 每个扫描、处理和入库操作带关联标识，日志可以从 API 请求追踪到文件操作和数据库事务。
- 日志不记录媒体内容，不暴露完整访问令牌或其他敏感配置。
- 设置页显示目录可用性、FFmpeg 可用性、最后扫描时间和待恢复操作数量。
- 应用启动恢复完成前，可以浏览文件库，但暂时禁止新的入库提交。

## 15. 测试策略

### 15.1 单元测试

- `InboxItem` 状态迁移和 `allowed_actions`。
- 文件稳定性判断、扫描幂等和处理器适用性。
- MP4/M4A 配对和处理计划顺序。
- 作者多选、系列单选和标签多选约束。
- 冲突后缀计算和冲突选择失效规则。

### 15.2 集成测试

使用临时目录、临时 SQLite 和小型媒体样本覆盖：

- 普通图片和视频的完整入库。
- MP4 与 M4A 合并、输出验证和源文件清理。
- 处理失败、重试和应用重启恢复。
- Prepare、Commit 和 Cleanup 各阶段中断。
- 文件移动成功但数据库提交失败。
- 清理失败后不撤销已入库资产，并能够后续重试。
- 名称冲突、内容冲突和替换恢复。

真实 FFmpeg 测试使用仓库内小型、可再分发的固定样本；不依赖网络下载。

### 15.3 API 与前端测试

- API 合约测试验证命令幂等、状态和错误结构。
- 前端组件测试验证图库状态、抽屉表单和分类选择。
- 端到端测试覆盖普通入库、自动预处理、处理失败、三种冲突选择和正式库资料编辑。
- 禁止用源代码字符串存在性代替用户行为测试。

## 16. 实施分期

### 阶段 1：新应用基础

建立独立应用入口、配置校验、SQLite 迁移、存储接口、状态机、操作日志和测试基础。此阶段不连接旧数据库。

### 阶段 2：最小入库闭环

完成普通图片和普通 MP4 的扫描、稳定性判断、预览、草稿标注、正式移动和文件库查询，形成第一个可演示的纵向切片。

### 阶段 3：可扩展预处理

加入处理器协议、注册表、计划器、持久化执行器，以及首个 MP4/M4A 合并处理器。

### 阶段 4：冲突与恢复

实现暂存目录、三阶段入库、启动恢复、Windows 式冲突选择和延迟清理。

### 阶段 5：完整图库体验

完成批量标注、词表管理、组合筛选、显示名称编辑、SSE 状态更新和设置诊断。

### 阶段 6：切换与旧系统退场

使用真实文件副本完成验收，随后冻结旧应用。旧代码删除、归档、文档清理和入口切换单独设计、单独提交，不能混入新应用首版实现。

## 17. 验收标准

新系统必须满足以下可观察结果：

1. 用户可以配置互不冲突的待入库、正式库和工作目录。
2. 图片和普通视频在下载完成并稳定后只被发现一次。
3. 同名 MP4 与 M4A 自动生成处理计划、完成合并并验证音视频流。
4. 用户可以为媒体设置多作者、零或一个系列、多标签和可选显示名称。
5. 正式入库后文件位于正式目录，默认实际文件名不变。
6. 合并场景入库提交成功后，原 MP4 和 M4A 被清理；提交失败时原文件仍然存在。
7. 名称或内容冲突必须展示双方预览，并按用户选择跳过、保留两者或替换。
8. 正式库可以按名称、作者、系列、标签和媒体类型检索。
9. 修改显示名称不会改变物理文件名。
10. 在处理或入库任意阶段终止应用并重启，不会丢失源文件、重复创建资产或留下无法解释的正式文件。
11. 一个文件失败不会阻塞其他文件继续处理和入库。

## 18. 主要风险与控制

- **文件丢失风险**：通过单一存储模块、三阶段入库、完整哈希、操作日志和提交后清理控制。
- **处理器扩展重新形成条件分支**：通过适用性检测、声明式优先级和统一计划器控制。
- **前后端状态不一致**：状态机只存在于后端，API 返回 `allowed_actions`。
- **旧系统继续影响新设计**：新目录、新数据库和禁止旧模块依赖形成硬隔离。
- **首版范围膨胀**：网络下载、AI、多用户和旧业务域明确排除。
- **旧代码过早删除**：新系统通过真实文件副本验收前，旧应用保持不动。

本设计形成一个完整但边界明确的首版媒体入库系统。后续实施计划应按纵向切片拆分任务，并为每个阶段定义可运行的验证命令和回滚边界。
