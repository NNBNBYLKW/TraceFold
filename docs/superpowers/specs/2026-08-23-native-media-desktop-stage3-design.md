## 1. 目标

Stage 3 在已验收的 Stage 2 扫描、资料草稿、预览和普通文件安全入库闭环上，增加可扩展的前置处理流水线，并交付第一个内置处理器：同名 MP4/M4A 无重编码合并。

面向用户的路径保持简单：

> 刷新 → 选择需要处理的项目 → 手动开始处理 → 可选标注 → 正式入库

前置处理成功后不会自动入库。用户仍然可以检查预览、编辑资料并明确点击“正式入库”。原始 MP4 和 M4A 只在正式资产提交且验证成功后由入库清理阶段删除。

## 2. 已确认的产品决策

1. 前置处理只由用户手动触发，不因扫描、启动或资料保存自动执行。
2. 关闭软件时终止本软件启动的 FFmpeg，将运行中和未开始的队列任务持久化为已中断；下次启动不自动恢复。
3. 处理期间提供“停止处理”；停止当前任务后，应用仍在运行时队列继续执行下一个任务。
4. 同一时刻最多执行一个处理任务；用户可以将多个项目加入串行队列。
5. 卡片和右侧资料栏显示当前步骤和数字进度，不增加独立任务中心。
6. MP4/M4A 合并只是首个内置处理器；扫描、界面和入库服务不得写死该格式组合。
7. 处理器通过显式依赖注入注册，不动态加载外部 DLL、脚本或网络插件。
8. FFmpeg 和 FFprobe 随离线包提供；运行时不依赖系统 `PATH`，也不联网下载工具。
9. 处理器不能删除源文件，也不能写入正式文件库。
10. 处理成功后使用合并输出进行预览和正式入库；实际文件名仍采用原 MP4 文件名，显示名称仍只存在于资料中。

## 3. 范围

### 3.1 包含

- 可扩展的内置处理器契约和显式注册表。
- 不可变处理计划、持久化处理任务和单任务串行执行器。
- 排队、取消排队、开始、停止、中断、失败、重试和成功状态。
- 结构化步骤和数字进度。
- 受控 FFmpeg/FFprobe 进程适配层。
- `mp4_m4a_merge` 处理器。
- 处理输出的流验证、预览和入库衔接。
- 多源文件的提交后清理清单。
- 启动恢复、源变化失效和隔离工作目录清理。
- 包含媒体工具及许可证的 Windows 11 x64 离线 ZIP。

### 3.2 不包含

- 自动开始处理、处理成功后自动入库或自动续接中断任务。
- 多个处理任务并行执行。
- 多步骤依赖图、可视化工作流编辑器或通用 DAG 引擎。
- 外部插件、动态程序集、用户自定义 FFmpeg 参数或脚本。
- 重新编码、格式转换、图片转换、缩略图生成等第二种处理器。
- Stage 4 的冲突对比弹窗、跳过、两者都保留和替换。
- 批量标注、组合筛选和其他 Stage 5 功能。
- 网络下载、联网更新 FFmpeg 或遥测。

Stage 3 继续沿用 Stage 2 的冲突行为：检测到名称或内容冲突时进入 `ConflictBlocked`，保留所有源文件并阻止入库，不提供冲突解决选项。

## 4. 架构选择

采用“能力驱动的持久化处理队列”。没有采用以下两种方案：

- MP4/M4A 专用合并服务：实现较短，但会把第一个格式组合写入扫描、状态和界面主流程，后续扩展仍需重构。
- 通用 DAG 工作流引擎：灵活性超出当前需求，会增加配置、调度和恢复复杂度。

依赖方向保持为：

```text
Desktop → Application → Domain
Desktop → Infrastructure → Application / Domain
```

处理路径进一步约束为：

```text
界面 → 应用用例 → 计划器 / 持久化队列 → 处理器 → 媒体工具端口
                                                     ↑
                                                Infrastructure
```

ViewModel 不调用进程 API。处理器不引用 WinUI、EF Core、SQLite 或具体 `Process` 实现。基础设施不决定业务状态迁移。

## 5. 组件与职责

### 5.1 处理器契约

每个内置处理器实现统一契约，并声明：

- 稳定唯一的处理器键和版本。
- 所提供的能力标识。
- 所需输入角色和输出媒体类型。
- 对候选项目的适用性验证。
- 不可变处理计划的生成。
- 受控工作目录中的执行步骤。
- 输出验证规则。
- 稳定错误分类和是否可重试。

首个处理器的键和能力均为 `mp4_m4a_merge`。它接受一个视频主文件和一个音频伴随文件，生成一个 MP4 输出。

处理器只能通过应用层端口读取已批准的输入、请求媒体探测、请求受控进程执行并写入分配的任务目录。契约不暴露任意正式库路径或源文件删除操作。

### 5.2 处理器注册表

桌面组合根通过依赖注入显式注册全部内置处理器。注册表按能力标识解析处理器，并在启动时拒绝：

- 重复处理器键。
- 同一能力存在未明确优先级的多个实现。
- 空版本或不完整描述。

扫描器继续使用 Stage 2 的候选分组规则声明所需能力。扫描器本身不知道 FFmpeg，也不负责选择实现。

### 5.3 处理计划器

“开始处理”用例先重新验证项目状态和源文件，再由计划器选择处理器并创建不可变计划。计划至少记录：

- 计划标识、项目标识、处理器键和版本。
- 每个输入的角色、受控文件标识和源快照。
- 预期步骤、输出媒体类型和输出文件名。
- 唯一任务工作目录的相对路径。
- 创建时间和计划版本。

计划不能保存界面传入的任意绝对输出路径。重试创建新计划和新任务；旧任务作为诊断历史保留，旧的未验证输出不能复用。

### 5.4 持久化任务队列

`ProcessingJob` 保存：

- 计划标识、尝试序号和任务状态。
- 排队、开始和结束时间。
- 当前步骤、0–100 进度和最近更新时间。
- 输出快照。
- 稳定错误码、用户提示、可重试标记和日志关联标识。

数据库约束保证一个 `InboxItem` 同一时刻最多存在一个活动处理任务。重复点击“开始处理”返回已有任务，不创建重复任务。

### 5.5 单任务执行器

进程内后台执行器按持久化排队顺序领取任务，任意时刻只持有一个运行租约。领取和状态更新使用数据库并发控制，避免重复执行。

任务失败只影响对应项目。执行器在应用仍运行时完成一个任务后继续下一个；应用进入关闭流程后不再领取新任务。

### 5.6 媒体工具适配层

基础设施实现统一媒体工具端口，负责：

- 定位和检查包内 FFmpeg/FFprobe。
- 使用独立参数安全启动进程。
- 读取 FFmpeg 结构化进度。
- 捕获受限诊断输出。
- 按取消请求终止本次启动的进程树。
- 使用 FFprobe JSON 验证输入和输出媒体流。

处理器不直接构造 shell 命令，不直接管理进程生命周期。

## 6. 数据模型与迁移

Stage 3 增加或扩展以下持久化概念：

- `ProcessingPlan`：不可变计划头、处理器键和版本、预期输出与版本信息。
- `ProcessingPlanInput`：输入角色、源文件引用和源快照。
- `ProcessingJob`：一次排队或执行尝试及其状态、步骤、进度和错误。
- `ProcessedOutput`：已验证输出的受控相对路径、大小、修改时间、SHA-256、媒体类型和流摘要。
- `IngestCleanupEntry`：正式提交成功后可清理的源文件或工作文件快照。

源快照至少包含规范路径、大小、最后修改时间和已有的轻量身份；处理前为 MP4 和 M4A 计算并保存完整 SHA-256。正式入库前重新核对源 SHA-256，清理前再次按清理清单验证身份。

数据库唯一约束至少覆盖：

- 一个项目最多一个活动处理任务。
- 一个任务只有一个有效输出。
- 工作目录相对路径和任务标识的一致归属。
- 一个入库操作中的清理条目不重复。

迁移必须保留 Stage 1 目录设置和全部 Stage 2 项目、草稿、词表、资产与入库记录。已有 `RequiresProcessing` 项目迁移后保持该状态，不自动排队。

## 7. 项目与任务状态

### 7.1 `InboxItem` 可见状态扩展

```text
Analyzing
  → RequiresProcessing
  → ProcessingQueued
  → Processing
  → ReadyToTag

ProcessingQueued → RequiresProcessing       （取消排队）
Processing → ProcessingInterrupted          （停止、关闭或异常退出）
Processing → Failed                         （执行或验证失败）
ProcessingInterrupted / Failed → ProcessingQueued  （手动重试，新任务）
任一处理阶段发现源变化 → WaitingForStability
```

`Failed` 带失败阶段；处理失败在界面显示为“处理失败”。`ProcessingInterrupted` 是明确可见状态，不与工具错误混淆。

### 7.2 `ProcessingJob` 状态

```text
Queued → Running → Succeeded
Queued → Cancelled
Queued / Running → Interrupted
Running → Failed
```

任务状态和项目状态由同一个应用层事务协调更新。界面不能直接写入任何状态字段。

### 7.3 允许动作

- `RequiresProcessing`：可编辑资料、预览主 MP4、开始处理。
- `ProcessingQueued`：可编辑资料、查看队列状态、取消排队。
- `Processing`：可编辑资料、查看步骤与进度、停止处理。
- `ProcessingInterrupted`：可编辑资料、查看中断原因、重试。
- 处理阶段 `Failed`：可编辑资料、查看错误；错误可重试时显示重试。
- `ReadyToTag`：预览已验证输出、编辑资料、正式入库。

资料字段始终可选。开始前置处理不要求填写作者、系列、标签或显示名称。

## 8. 完整处理流程

### 8.1 发现与手动排队

Stage 2 已将同一目录、同基本名称且扩展名不区分大小写匹配的 MP4/M4A 分为一个项目，并声明 `mp4_m4a_merge` 能力。Stage 3 注册该能力后，项目仍先进入 `RequiresProcessing`，不会自动执行。

用户点击“开始处理”时：

1. 刷新尚未保存的资料草稿。
2. 确认项目仍为 `RequiresProcessing`、没有活动任务且目录配置有效。
3. 重新运行分组与适用性检查。
4. 取得 MP4 和 M4A 的当前快照并计算完整 SHA-256。
5. 创建新计划和 `Queued` 任务，将项目置为 `ProcessingQueued`。

### 8.2 执行

执行器领取任务后：

1. 创建并验证唯一任务目录：`processing/{job-id}/`。
2. 重新核对输入路径、快照和 SHA-256。
3. 用 FFprobe 检查 MP4 包含视频流、M4A 包含音频流，并取得可靠时长。
4. 在任务目录中生成唯一临时输出，例如 `merged.partial.mp4`。
5. 用 FFprobe 验证输出。
6. 再次核对两份输入未变化。
7. 将临时输出在同一任务目录内原子改名为有效输出，并保存 `ProcessedOutput`。
8. 在同一个数据库事务中把任务置为 `Succeeded`、项目置为 `ReadyToTag`。

### 8.3 MP4/M4A 合并规则

FFmpeg 使用显式流映射：第一个输入的视频流和第二个输入的音频流。媒体流采用复制模式，不做重新编码；输出启用适合普通播放的 MP4 布局优化。

参数通过进程参数列表传递，并使用无交互、拒绝覆盖唯一输出的模式。用户文件名、资料文本或外部配置不能成为额外 FFmpeg 参数。

输出采用原 MP4 的基本名称和 `.mp4` 扩展名。显示名称保持独立，不影响输出和正式文件名。

### 8.4 输出验证

仅 FFmpeg 退出码为 0 不构成成功。FFprobe 必须确认：

- 文件存在且大小大于零。
- JSON 可解析且容器可读取。
- 至少包含一个视频流和一个音频流。
- 输出具有有效时长。
- 输出仍位于当前任务的受控工作目录。

验证成功后计算输出 SHA-256。任何检查失败均不能生成 `ProcessedOutput`。

## 9. 进度与桌面交互

待入库页继续使用资源管理器式三栏，不增加任务中心。

卡片和右侧资料栏显示：

- “需要前置处理”“排队中”“处理中”“已中断”“处理失败”或“可正式入库”。
- 处理器的用户可读名称，例如“合并视频和音频”。
- 当前步骤：“检查源文件”“合并音视频”“验证输出”。
- 0–100 的数字进度。
- 当前状态允许的主操作。

进度映射固定为：

- 检查源文件：0–5。
- 合并音视频：5–95；根据 FFmpeg `out_time` 和 FFprobe 得到的预期时长计算并钳制。
- 验证输出：95–99。
- 数据库提交成功：100。

进度只能单调增加。刷新界面或重新选择项目时从持久化任务读取最近进度，不从 ViewModel 自行推算。

成功后右侧视频播放器解析 `ProcessedOutput`，而不是原视频主文件。预览失败沿用 Stage 2 规则：显示错误但不删除输出；正式入库仍执行自己的完整验证。

## 10. 停止、关闭与启动恢复

### 10.1 手动停止

用户停止当前任务时：

1. 应用层记录取消请求。
2. 媒体工具适配层只终止该任务启动的 FFmpeg 进程树。
3. 执行器等待进程退出并隔离未验证输出。
4. 任务和项目持久化为 `Interrupted` / `ProcessingInterrupted`。
5. 应用仍在运行时，执行器领取下一个排队任务。

停止不是处理失败，不增加错误重试次数。用户重试时从头执行，不续传旧输出。

### 10.2 取消排队

未开始的任务可以取消。取消在一个事务内将任务置为 `Cancelled`，项目退回 `RequiresProcessing`，不会创建工作目录。

### 10.3 关闭软件

关闭流程停止接受新任务并停止领取队列。当前 FFmpeg 被终止，当前任务和所有尚未开始的 `Queued` 任务统一置为 `Interrupted`，对应项目显示“已中断”。关闭流程不自动开始下一个任务。

### 10.4 异常退出恢复

启动恢复在执行器开始领取任务前运行。数据库中残留的 `Queued` 或 `Running` 任务均转为 `Interrupted`；属于这些任务的未验证输出被隔离并安排受控清理。启动后不自动重试。

若进程已经不存在，恢复不根据旧进程 ID 操作其他系统进程。用户必须点击“重试”创建新的计划和任务。

## 11. 源变化和输出失效

以下任一情况使计划或有效输出失效：

- MP4 或 M4A 消失。
- 规范路径、大小、修改时间或 SHA-256 与计划不一致。
- 分组规则不再返回原能力。
- 处理器版本不再可用。
- 有效输出丢失、被修改或验证失败。

排队期间发现变化时取消旧任务；处理期间发现变化时停止当前任务。项目回到 `WaitingForStability`，保留资料草稿并显示源变化提示。重新稳定和分析后，只有新的手动操作才能再次排队。

已处理项目在正式入库前必须再次验证输入和输出身份。不能证明一致时绝不继续入库，也不删除任何源文件。

## 12. 正式入库衔接与清理

Stage 3 将 Stage 2 的普通单源入库输入抽象为“已准备媒体输入”：

- 普通项目使用稳定的原始媒体文件。
- 已处理项目使用唯一、已验证的 `ProcessedOutput`。

二者共用同一套冲突检测、暂存、正式文件提交、数据库提交和目标验证，不建立第二条处理后入库流程。

已处理项目开始入库前必须确认：

- 项目为 `ReadyToTag`，最新草稿已保存。
- MP4、M4A 和处理输出均与记录一致。
- 输出仍通过音视频流验证。
- 没有其他活动处理或入库操作。

`IngestOperation` 记录最终输入快照，并为 MP4、M4A、处理输出和入库暂存建立清理清单。正式文件与数据库事务提交并重新验证后，清理服务才按清单逐项处理。

删除每个原始源文件前必须再次验证规范路径和完整 SHA-256。无法证明身份、源已变化或删除失败时保留该文件，并使操作进入 `CleanupPending`。清理可以幂等重试；已经成功入库的正式资产不回滚。

处理输出若通过移动成为正式文件，则清理清单将其视为已经消耗；若入库采用复制，则提交成功后再删除工作区副本。处理器本身永远不执行这些删除。

## 13. 工作目录和路径安全

每个任务只能使用：

```text
{configured-work-root}/processing/{job-id}/
```

所有创建、改名和删除操作都必须：

1. 规范化根目录和目标路径。
2. 验证最终路径仍在对应任务目录中。
3. 拒绝重解析点和目录逃逸。
4. 验证任务标识与数据库归属。

停止或失败产生的半成品不能用于预览或入库。可确认属于任务目录的半成品可以立即安全清理；清理失败则保留带错误码的记录，由后续启动或用户重试再次清理。无法证明归属的文件保持不动。

## 14. FFmpeg/FFprobe 分发与诊断

发布结构固定包含：

```text
tools/ffmpeg/ffmpeg.exe
tools/ffmpeg/ffprobe.exe
tools/ffmpeg/LICENSE-or-COPYING
tools/ffmpeg/THIRD-PARTY-NOTICES
```

实际许可证文件名可以与所选发行版一致，但发布清单必须明确记录并检查。构建产物同时记录两个可执行文件的版本和 SHA-256。

生产运行时只解析应用基目录下的包内路径，不回退到系统 `PATH`。开发和测试通过依赖注入提供显式工具目录，不允许业务代码自行搜索机器安装位置。

工具缺失、不可执行或版本探测失败时：

- 禁用“开始处理”和“重试处理”。
- 在项目资料栏和设置诊断中显示稳定错误码。
- 保持扫描、资料编辑、普通预览、普通文件入库和正式库浏览可用。
- 不尝试联网修复。

日志可以记录任务 ID、处理器键、工具版本、稳定错误码、受控路径和截断后的工具诊断；不记录媒体内容、资料正文或未受控任意路径。

## 15. 错误分类

错误至少分为：

- 配置错误：工作目录或包内工具无效。
- 输入错误：源缺失、变化、流不符合处理器要求。
- 执行错误：FFmpeg 无法启动、异常退出或被外部终止。
- 验证错误：输出缺失、不可解析、缺少视频流或音频流。
- 清理错误：受控临时文件无法删除。
- 内部错误：持久化或未分类异常。

每个错误包含稳定代码、用户可理解提示、日志关联标识和可重试标记。原始 FFmpeg 文本只写入受限日志，不直接作为主界面提示。

一个任务失败不能阻止其他项目扫描、标注、普通入库或后续排队任务执行；只有应用级数据库故障才暂停整个执行器。

## 16. 测试策略

### 16.1 Domain

- 处理器描述和注册约束。
- 项目与任务状态迁移及 `AllowedActions`。
- 中断与失败语义不同。
- 计划不可变、重试创建新尝试。
- 源变化和处理器版本变化使输出失效。

### 16.2 Application

- 手动开始才创建任务，扫描和启动不自动排队。
- 重复开始命令保持幂等。
- 多项目按顺序排队且最多一个运行。
- 取消排队、停止当前、队列继续和关闭时全队列中断。
- 启动恢复不自动重试。
- 步骤与进度单调持久化。
- 处理成功返回 `ReadyToTag`，不自动入库。
- 处理输出使用现有冲突检测和正式入库路径。

### 16.3 Infrastructure

测试只使用临时 SQLite、临时待入库目录、临时正式库和临时工作目录：

- EF Core 迁移保留 Stage 2 数据。
- 真实 FFmpeg 合并仓库内固定 `paired.mp4` 和 `paired.m4a`。
- 路径包含空格、中文和特殊字符。
- FFprobe 验证输出包含视频流和音频流。
- 工具缺失、启动失败、异常退出、无效输入和无效输出。
- 停止只终止本任务进程树。
- 半成品隔离、受控清理和路径逃逸拒绝。
- 源变化、输出篡改和清理失败。
- 正式提交前不删除 MP4/M4A；提交验证后按清单清理。

自动测试不得读取、移动或删除用户配置的真实目录。

### 16.4 Desktop

- 不同状态下按钮的可见和启用规则。
- 卡片和资料栏显示处理器名称、步骤、数字进度和错误。
- 取消排队、停止和重试命令只作用于选中项目。
- 成功后视频预览解析处理输出。
- 普通图片、普通视频、资料编辑、词表和正式库回归。

### 16.5 关闭与恢复

- 运行中关闭后 FFmpeg 不残留。
- 排队和运行任务重启后统一显示已中断。
- 重启不自动生成新计划或运行任务。
- 旧进程 ID 不会导致终止无关进程。
- 未验证半成品不能预览或入库。

## 17. 离线包

产物命名为：

```text
TraceFold-MediaDesktop-Stage3-win-x64.zip
```

离线包必须：

- 自带 .NET、Windows App SDK、FFmpeg、FFprobe 和对应许可证。
- 解压后直接启动独立窗口，不打开浏览器或保留命令行窗口。
- 不依赖网络、系统 FFmpeg、Visual Studio、SDK 或开发环境变量。
- 不包含源码、PDB、用户数据库、媒体、日志、工作目录或测试结果。
- 生成文件清单和 ZIP 的 SHA-256。

发布检查通过清空冒烟进程的 `PATH` 并验证实际工具路径位于解压目录，证明没有使用本机 FFmpeg。没有虚拟机时，这构成本阶段的本机离线依赖检查；仍需保留未来在干净 Windows 11 x64 机器上复验的发布门槛。

## 18. 人工验收

1. 使用三个隔离测试目录启动 Stage 3 测试包。
2. 将同名 MP4 和 M4A 放入待入库目录并立即刷新。
3. 确认只显示一个“需要前置处理”项目，且没有自动开始。
4. 编辑可选显示名称、作者、系列和标签，确认可以在处理前保存。
5. 点击“开始处理”，观察“排队中/处理中”、步骤和数字进度。
6. 处理成功后播放合并输出，确认同时有画面和声音。
7. 确认处理成功但尚未正式入库时，原 MP4 和 M4A 仍存在。
8. 点击“正式入库”，确认正式文件沿用原 MP4 文件名，显示名称没有修改物理文件名。
9. 确认正式资产提交并验证成功后，原 MP4、M4A 和无用工作文件被清理。
10. 为两个项目开始处理，确认一个运行、一个排队。
11. 停止当前项目，确认它显示已中断且下一个项目开始运行。
12. 处理过程中关闭软件，确认没有残留 FFmpeg；重启后任务显示已中断且不会自动重试。
13. 修改任一源文件，确认旧输出失效且不能正式入库。
14. 验证工具缺失诊断不会阻止普通图片或视频入库。
15. 回归普通图片、普通视频、资料、词表、预览和正式库流程。

## 19. 验收标准

Stage 3 完成必须同时满足：

1. 扫描器、ViewModel 和入库服务均不包含 MP4/M4A 合并专用分支；格式特性位于处理器及已有分组规则中。
2. 新增内置处理器无需修改扫描与界面主流程。
3. 用户明确点击后才处理，处理成功后仍需明确点击正式入库。
4. 任意时刻最多一个 FFmpeg 任务运行，多个项目可以持久化排队。
5. 停止和关闭能终止本软件拥有的进程，且不会自动恢复中断任务。
6. 输出经 FFprobe 确认同时包含视频流和音频流后才可预览或入库。
7. 正式入库验证成功前，原始 MP4 和 M4A 在任何失败、中断或冲突情况下均保留。
8. 正式提交后多源清理可幂等重试，不能越出受控目录。
9. 普通图片和视频的 Stage 2 主流程无回归。
10. Stage 3 离线 ZIP 使用包内 FFmpeg/FFprobe，无网络和系统工具依赖。

## 20. 实施边界

实施应按契约、状态、持久化、媒体工具、首个处理器、执行器、入库衔接、界面、打包的顺序建立纵向检查点。每个检查点先以测试定义行为，再增加最小实现。

本阶段只进行服务于前置处理的定向重构。不得借机实现 Stage 4 冲突选择、Stage 5 批量功能或无关界面改版。

本规格经用户审阅后，下一步是为 Stage 3 编写独立实施计划；在计划确认前不开始功能代码。
