## 1. 目标

Stage 5C-C 完成原生媒体桌面端 Stage 5 的质量收口，解决两个相互依赖的问题：

1. 把当前各页面分散的尺寸、间距、颜色和布局行为收敛为统一的 Windows 视觉系统，在保持资源管理器式三栏和现有操作逻辑的前提下，支持 `1024×720` 最低窗口与 Windows 明暗主题。
2. 建立真正驱动发布版原生窗口的离线 Windows UI Automation 验收链路，覆盖文件管理主流程，并同时核对界面、数据库、文件系统、进程和清理结果。

本阶段不重做产品信息架构，不增加业务功能，也不以测试替身代替真实发布程序。用户看到的主流程仍然是：

```text
设置目录
  → 扫描待入库文件
  → 单个或批量补充资料
  → 执行可扩展前置处理
  → 处理冲突并正式入库
  → 在正式文件库筛选和批量维护
  → 管理词表并查看系统诊断
```

## 2. Stage 5C 边界

Stage 5C 是“管理与质量收口”阶段，按独立纵向切片交付：

1. **Stage 5C-A：词表管理增强**。已完成词表引用查询、显式合并、安全批量删除和会话内撤销。
2. **Stage 5C-B：设置与系统诊断**。已完成双页签设置、模块化只读诊断、脱敏摘要和安全排查入口。
3. **Stage 5C-C：视觉与 Windows UI Automation 收口**。本规格覆盖视觉资源、响应式三栏、自动化可访问契约、发布窗口端到端验收、证据与独立工具包。

Stage 5C-C 完成后，Stage 5 不再增加新的管理能力。后续 Stage 6 仍按上位规格处理旧 Web 版本的切换、冻结和退役；该工作不属于本规格。

## 3. 已确认的产品与技术决策

1. 保留现有资源管理器式三栏、页面导航和操作流程，只统一视觉语言与响应式行为。
2. 最低支持窗口为 `1024×720`。
3. 窗口宽度 `>=1280` 时保持完整三栏；`1024–1279` 时左侧收缩为图标导航，右侧资料栏改为抽屉。
4. 文件列表采用平衡密度，目标行高为 38 px。
5. 软件自动跟随 Windows 明暗主题，不增加应用内主题开关。
6. UI Automation 覆盖关键端到端用户链，不追求逐个控件穷举。
7. 自动化只驱动 TraceFold 自己拥有的窗口和对话框；Windows 文件夹选择器、资源管理器和其他系统窗口由契约测试及人工验收覆盖。
8. 设置目录可直接在 TraceFold 文本框中输入并保存，因此端到端主链不依赖系统文件夹选择器。
9. 自动化驱动采用固定版本、固定 SHA-256 的 Microsoft `winapp` 独立命令行工具和 PowerShell 场景脚本，不依赖 WinAppDriver、Appium、后台服务或机器级安装。
10. 每个场景使用独立临时数据根、数据库、三个媒体目录和固定合成媒体；绝不访问用户真实数据。
11. 自动化启动真实发布版 `TraceFold.Media.exe`，通过现有 `TRACEFOLD_MEDIA_DESKTOP_DATA_ROOT` 仅为被测进程指定隔离数据根。
12. 不增加测试专用业务入口、跳过条件、数据库注入命令或隐藏管理按钮。
13. 检测到普通 TraceFold 实例正在运行时停止验收并提示用户关闭；验收程序绝不终止用户进程。
14. 产品离线包不包含自动化工具、脚本或测试媒体；验收工具包独立生成。
15. 当前 Windows 主机上的隔离验收是本阶段必测项；全新机器或虚拟机验证是后续发布增强项，不阻塞本阶段，因为当前用户没有虚拟机。

## 4. 范围

### 4.1 包含

- 集中的 WinUI 视觉资源与语义化尺寸、间距、颜色和状态资源。
- Shell、待入库、正式文件库、词表管理和设置页面的视觉一致性收口。
- 完整三栏与紧凑导航加资料抽屉两种响应式状态。
- `1024×720` 下的内容滚动、弹窗可达性、焦点恢复和键盘路径。
- 明暗主题、非纯颜色状态表达和 38 px 文件列表密度。
- 关键静态控件的稳定 `AutomationId`、中文可访问名称和正确 UIA Pattern。
- 动态列表项的可搜索可访问名称、稳定子控件边界和选择模式。
- 固定并校验的 `winapp` 工具、PowerShell 编排、固定合成测试媒体和一键启动器。
- 真实发布窗口的设置、扫描、标注、前置处理、入库、文件库、词表和诊断端到端场景。
- 界面、数据库、文件系统、进程和清理结果的双重或多重断言。
- JSON、纯文本、失败截图、UIA 控件树和视觉截图索引。
- Stage 5C-C 独立原生应用包、独立自动化工具包、校验值和人工补充验收指南。

### 4.2 不包含

- 修改扫描、资料关系、命名、前置处理、冲突、入库、批量编辑、词表或诊断业务规则。
- 新增媒体处理器、文件格式、命名能力、维护任务或后台任务中心。
- 修改数据库结构、迁移或持久化格式。
- 自动驱动 Windows 文件夹选择器、资源管理器、系统剪贴板界面或其他外部应用。
- 引入 WinAppDriver、Appium、常驻服务、机器级安装器或联网运行依赖。
- 全屏像素级黄金图回归。
- 支持小于 `1024×720` 的完整业务操作；更小窗口可以受限，但不能崩溃或破坏数据。
- Stage 6 的旧 Web 版本切换、冻结和退役。

## 5. 总体架构

Stage 5C-C 在现有 Desktop → Application → Domain / Infrastructure 依赖方向之外增加独立验收基础设施，但不改变业务层依赖：

```text
TraceFold.Media.Desktop
  ├─ Semantic visual resources
  ├─ Responsive shell states
  ├─ Accessible page/control contracts
  └─ Existing ViewModels and application services
               │
               ▼
     Existing Application / Infrastructure

Separate UI acceptance toolkit
  ├─ one-click launcher
  ├─ PowerShell orchestrator
  ├─ pinned winapp.exe
  ├─ synthetic fixtures
  ├─ scenario definitions
  ├─ read-only result verifiers
  └─ reports / screenshots / UIA trees
               │
               ▼
  published TraceFold.Media.exe
  isolated TRACEFOLD_MEDIA_DESKTOP_DATA_ROOT
```

验收工具包是发布程序的外部使用者。它只能通过公开窗口行为、发布清单、受控文件系统结果和只读验证器观察结果，不能引用 Desktop 内部 ViewModel，也不能通过反射或测试后门直接改变业务状态。

### 5.1 方案取舍

响应式布局比较过三种方式：紧凑窗口使用右侧资料抽屉、始终压缩三栏、把资料固定移到列表下方。最终选择资料抽屉，因为它能在 `1024×720` 下保住文件列表宽度和高度，也不改变宽屏三栏习惯；始终三栏会过度截断内容，下方资料区会持续挤占浏览高度。

Windows UI Automation 比较过四种方式：固定 `winapp` CLI、基于 FlaUI.UIA3 的专用 C# 驱动、直接封装 Windows `IUIAutomation`、继续使用 WinAppDriver。最终选择固定 `winapp` CLI，因为它直接支持 WinUI 3、可独立分发、脚本接口足够覆盖现有主链，并且不要求常驻服务。FlaUI 是可行备选但需要维护更多驱动代码；直接封装 `IUIAutomation` 控制力最强但成本最高；WinAppDriver 的服务和安装模型不符合本阶段离线、免安装约束。

## 6. 视觉系统

### 6.1 语义资源

建立集中 WinUI `ResourceDictionary`，资源按用途命名，而不是按某个页面或当前像素值命名。至少覆盖：

- 完整和紧凑导航宽度；
- 三栏间距、中间内容最小宽度、资料栏标准宽度；
- 页面标题、分区、卡片和表单间距；
- 38 px 文件行与紧凑辅助行；
- 主要、次要、危险和文字按钮层级；
- 健康、提醒、失败、排队、运行和禁用状态；
- 焦点边框、选择背景、分隔线和浮层背景；
- 明暗主题下的对应主题资源。

本规格中的布局宽度、高度和行高均指 WinUI 有效像素（DIP），不是未经缩放换算的物理屏幕像素。自动化根据当前 DPI 换算窗口尺寸，并在报告中同时记录缩放比例和实际内容视口，避免高缩放显示器把 `1024×720` 误测为更小布局。

页面 XAML 引用语义资源，不继续复制硬编码尺寸。个别控件因内容需要使用局部值时必须说明原因，不能重新形成页面级私有设计系统。

### 6.2 响应式状态

响应式行为由 Shell 和页面容器的 `VisualStateManager` 与窗口宽度触发，不写入业务 ViewModel。业务选择、筛选、搜索和任务状态不因窗口状态切换而重建。

#### 完整模式：`>=1280`

- 左侧为固定紧凑宽度的文字加图标导航。
- 中间文件区获得全部剩余宽度。
- 右侧资料栏常驻，使用统一标准宽度。
- 三栏之间使用统一分隔和间距，不通过大面积空白形成层级。

#### 紧凑模式：`1024–1279`

- 左侧收缩为图标导航，并保留工具提示与中文可访问名称。
- 中间文件区获得主要空间。
- 右侧资料栏不占用固定列，改为应用内右侧抽屉。
- 选中文件更新当前选择，但不会仅因选择而抢走列表焦点。
- 用户主动打开资料抽屉后，焦点进入抽屉标题或第一个可操作控件。
- 关闭按钮和 `Esc` 都可关闭抽屉；关闭后焦点返回原选中文件行。
- 选择另一文件时抽屉内容原位更新，不叠加第二层抽屉。
- 无选择时抽屉关闭，相关动作禁用。

跨断点切换必须保留当前页面、文件选择、批量选择、搜索、筛选、编辑草稿和滚动上下文。资料栏中的未保存草稿按照现有页面生命周期规则保留，不因视觉状态切换额外提交或丢弃。

### 6.3 最低窗口、滚动与对话框

`1024×720` 下：

- 页面头部、搜索筛选区和主要操作不得互相覆盖；
- 中间列表仍有可用浏览高度；
- 页面和长表单使用明确的内容滚动区；
- 应用自有对话框保持标题、内容、错误信息和确认/取消按钮可达；
- 内容不足时不人为拉伸空白，内容过长时滚动而不是裁切按钮；
- `Tab`、`Shift+Tab`、方向键、Enter、Space 和 Esc 路径保持可预测。

小于最低窗口时允许布局受限，但应用必须保持可关闭、不可发生未处理异常，且不得执行非用户确认的业务操作。

### 6.4 主题和状态表达

软件通过 WinUI 主题资源自动跟随 Windows 明暗主题，不持久化独立主题设置。状态不能只依赖颜色：图标、文字、可访问名称或形状至少提供第二种表达。明暗主题切换不能触发页面重新加载、任务重试或编辑状态丢失。

## 7. UI Automation 可访问契约

### 7.1 稳定标识

下列关键边界必须有稳定、语言无关且不随视觉布局变化的 `AutomationId`：

- 主窗口、Shell 导航和每个导航目标；
- 页面标题、搜索框、筛选器、刷新和主要命令；
- 文件列表、选中数量和资料栏/资料抽屉；
- 显示名称、作者、系列、内容标签及其提交动作；
- 前置处理状态与动作；
- 正式入库、重试、失败记录和冲突对话框动作；
- 正式文件库批量动作、撤销与命名相关入口；
- 词表类型、搜索、编辑、合并、删除和确认对话框；
- 设置页签、目录字段、自动扫描和保存；
- 诊断总体状态、刷新、摘要与各诊断分组。

视觉模式只能改变布局，不能改变同一逻辑控件的 AutomationId。动态文件行不要求测试依赖数据库生成 ID；行容器暴露合成测试文件的可访问名称，行内动作使用稳定模板标识和正确父子关系。

### 7.2 可访问名称与模式

- 面向用户的中文名称描述控件用途，而不是重复图标字符或内部字段名。
- 按钮、切换、文本输入、选择、列表和对话框分别暴露正确的 Invoke、Toggle、Value、Selection 或 Window 模式。
- 屏幕阅读器可以读出文件名称、媒体类型、状态和选中状态。
- 错误、排队、成功和禁用原因具有文字结论。
- 只有原生 WinUI 暴露不足时才增加自定义 `AutomationPeer`；普通控件优先使用平台默认能力。

### 7.3 契约测试

Desktop 结构测试继续验证 AutomationId、可访问名称和关键 XAML 关系；真实 UIA 场景验证发布窗口中控件确实可发现和可操作。两个层级同时存在，避免“XAML 写了标识但运行时自动化树不可用”。

## 8. 自动化工具与分发

### 8.1 驱动选择

使用 Microsoft `winapp` 独立 CLI 的发布 ZIP。仓库保存一个锁定清单，记录：

- 工具名称与精确版本；
- 官方发布来源；
- 原始文件名；
- SHA-256；
- 支持的 Windows 和应用架构；
- 本项目使用的命令能力。

实施时选定一个通过本项目兼容性试验的正式发布版本并固化清单；后续升级必须显式更新版本、哈希和兼容性测试，不能静默下载最新版。

验收工具包内包含已校验二进制，因此运行时完全离线。脚本启动前重新计算 SHA-256；不匹配即阻塞，不尝试联网修复。

### 8.2 工具包结构

独立工具包至少包括：

```text
TraceFold-MediaDesktop-Stage5C-C-UiAcceptance-win-x64/
  Run-Stage5CC-Acceptance.cmd
  scripts/
  tools/winapp/
  fixtures/
  manifests/
  README.txt
```

双击 `.cmd` 后调用固定 PowerShell 编排脚本，显示当前阶段和结果路径。无论成功、失败或阻塞，启动窗口都保留最终摘要并等待用户关闭，避免只出现一闪而过的命令行窗口。

产品 ZIP 与工具包 ZIP 各自生成 SHA-256。产品包不得包含 `winapp`、PowerShell 测试脚本、固定夹具、自动化报告模板或自动化专用清单。

## 9. 隔离环境与安全所有权

每个场景创建新的临时根，包含：

- 数据根与 SQLite 数据库；
- 待入库目录；
- 正式文件库目录；
- 工作目录；
- 场景结果和临时日志目录；
- 固定合成图片、视频和同名 MP4/M4A 前置处理夹具。

根目录创建包含高熵随机令牌的本次运行所有权标记，记录运行 ID、创建者和规范根路径。所有删除、清空和回收操作必须同时满足：

1. 路径位于本次运行创建的明确临时父目录内；
2. 所有权标记存在且内容匹配；
3. 规范路径不是用户目录、仓库根、磁盘根、产品包目录或其他宽泛位置；
4. 目标不是逃离根目录的重解析点。

任一检查失败时拒绝删除并报告清理失败。脚本不得枚举用户媒体目录，也不得复用用户现有数据库。

`TRACEFOLD_MEDIA_DESKTOP_DATA_ROOT` 只设置在被测进程环境中，不永久写入用户或系统环境变量。场景之间不复用数据库、设置或媒体目录，确保顺序独立。

## 10. 自动化执行流程

### 10.1 预检

运行前依次确认：

- 产品包目录、发布清单、Stage 检查点、产品版本和源提交一致；
- `winapp` 版本和 SHA-256 与锁定清单一致；
- 当前为可交互且未锁定的 Windows 桌面会话；
- Windows UI Automation 能枚举桌面；
- 没有普通 `TraceFold.Media` 实例正在运行；
- 没有由本次运行之外拥有的 TraceFold、FFmpeg 或 FFprobe 进程会被纳入清理。

预检失败记为 `Blocked` 并停止，不修改程序设置，不终止用户进程。

### 10.2 启动与附加

1. 创建场景临时根并复制固定夹具。
2. 为子进程设置隔离数据根和必要的场景环境，不改变系统环境。
3. 启动发布版 `TraceFold.Media.exe`，记录应用 PID、启动时间和子进程所有权。
4. 通过 PID 附加 UIA 驱动，并等待稳定主窗口 AutomationId。
5. 主窗口在规定时间内未出现时保存桌面截图、进程状态和启动日志，然后失败退出。

### 10.3 主链场景

一个全新环境中的主链依次验证：

1. 导航到设置并直接输入三个隔离目录，保存后确认状态。
2. 回到待入库并触发扫描，确认固定文件被发现。
3. 为单个文件设置多位作者、一个系列和多个内容标签。
4. 对多选文件执行批量资料操作并确认选中数量和结果。
5. 识别并执行同名 MP4/M4A 前置处理，等待排队、运行、完成与右侧资料自动刷新。
6. 正式入库并确认待入库项消失、正式库项出现、实际文件移动且原始 MP4/M4A 不保留。
7. 在正式文件库执行组合筛选、批量资料维护、显示名称或命名相关操作及撤销。
8. 在词表管理执行安全的新增、编辑、合并或删除验证。
9. 在系统诊断完成一次检查并确认总体状态与关键分组。

主链使用软件实际业务服务和数据库，不伪造任务完成事件。

### 10.4 独立场景

以下场景分别使用新的根和应用进程：

- 入库目标冲突的“保留两者”“替换”“跳过/取消”等现有选择及预览行为；
- 批量资料、撤销和部分失败反馈；
- `1024×720`、`1280×800` 和更宽窗口下的响应式状态；
- Windows 明暗主题下的关键页面；
- 空列表、加载、排队、失败、恢复和禁用状态；
- 仅键盘完成导航、选择、打开/关闭资料抽屉和确认应用自有对话框；
- 单实例保护和普通实例已运行时的安全阻塞；
- 诊断刷新、结果保留和退出后的进程清理。

自动化不打开或操纵系统文件夹选择器。相关按钮是否调用已注册安全边界由 Desktop 契约测试验证，实际系统窗口行为留在人工清单。

## 11. 断言策略

每个有业务意义的步骤至少验证两个观察面：

1. **界面面**：控件状态、文字结论、选择、焦点、对话框、资料栏或抽屉内容。
2. **事实面**：文件树、数据库只读快照、任务状态、包清单或进程状态。

事实验证复用或扩展现有包级探针和安全只读验证器。验证器不能为了测试方便改变状态，也不能让 UI 场景绕过正常命令。示例：

- 扫描后既确认文件行出现，也确认发现记录存在；
- 前置处理后既确认“完成”，也确认输出媒体存在且原始同名源的生命周期符合业务规则；
- 入库后既确认界面移动到正式库，也确认源文件、目标文件和数据库资料关系一致；
- 退出后既确认窗口消失，也确认本次运行拥有的进程树全部结束。

## 12. 失败、超时与清理

### 12.1 超时与重试

- 每个场景、步骤和状态等待都有明确超时。
- 允许重新执行纯观察型的查找、等待和读取。
- 不自动重复点击正式入库、删除、替换、合并、确认冲突等有副作用的动作。
- 控件状态不确定时先保存证据并失败，不猜测操作是否已执行。
- 一个场景失败后不继续依赖它的后续步骤；独立场景可以继续运行，以获得完整报告。

### 12.2 失败证据

失败时保存：

- 运行 ID、场景、步骤编号和稳定错误码；
- 当前应用截图；
- 当前 UIA 控件树；
- 最近一次成功操作和正在等待的条件；
- 脱敏应用诊断日志；
- 文件、数据库、进程和所有权检查摘要。

报告不得包含用户名、机器名、用户路径、真实媒体、用户数据库内容或未脱敏异常正文。固定测试文件名可以出现在报告中。

### 12.3 进程与目录清理

清理位于统一最终处理阶段：

1. 请求应用正常关闭并等待退出。
2. 若超时，只终止本次运行记录并确认拥有的进程树。
3. 等待本次运行拥有的 FFmpeg 和 FFprobe 退出。
4. 提取结构化失败证据。
5. 重新验证所有权标记与规范路径。
6. 删除场景临时根。
7. 确认没有临时探针文件、被测进程或测试数据残留。

所有权不明的进程和目录永远不自动处理。清理失败使整次验收失败，不能只记录警告。

## 13. 视觉验收策略

不采用全屏像素级黄金图判断通过，因为 Windows DPI、字体渲染、驱动和系统版本会产生无业务意义的差异。自动化使用结构和几何断言：

- 窗口处于预期断点；
- 导航为完整或紧凑形态；
- 资料栏常驻或作为抽屉出现；
- 关键控件可见、可达且不互相覆盖；
- 关闭抽屉后焦点返回选中文件行；
- `1024×720` 下确认按钮和主要操作可滚动到达；
- 明暗主题下状态同时具有图标或文字表达。

自动化同时在以下尺寸生成截图：

- `1024×720`；
- `1280×800`；
- `1600×900` 宽屏尺寸。

明暗主题各保留待入库、正式文件库、词表管理、设置诊断和关键对话框截图，生成 HTML 或纯文本截图索引供人工快速浏览。截图只包含固定合成数据。

## 14. 报告模型

每次运行生成机器可读 JSON 和易读纯文本报告，至少包含：

- 运行 ID、开始/完成时间和总耗时；
- 产品版本、Stage 检查点、源提交和产品包 SHA-256；
- `winapp` 精确版本和 SHA-256；
- Windows 版本、显示缩放和测试窗口尺寸；
- 每个场景及步骤的 `Passed`、`Failed`、`Blocked` 或 `NotRun`；
- 稳定错误代码、脱敏证据相对路径和持续时间；
- 应用、FFmpeg、FFprobe 残留进程检查；
- 临时文件、临时目录和所有权清理结果；
- 截图索引位置。

任一必测场景 `Failed`、`Blocked` 或 `NotRun`，或者存在进程和测试数据残留，整体验收均不通过。报告自身生成失败也视为验收失败。

## 15. 测试策略

### 15.1 视觉资源和 Desktop 测试

- 页面引用语义资源，不复制旧硬编码值。
- 明暗主题资源键完整且类型匹配。
- 两个响应式断点与最低窗口行为。
- 三栏/抽屉切换保留页面、搜索、筛选、选择和编辑草稿。
- 资料抽屉打开、切换文件、Esc 关闭和焦点恢复。
- 38 px 文件行与键盘选择。
- 长表单和应用自有对话框在 `1024×720` 下可滚动到主要动作。
- 状态不只依赖颜色。

### 15.2 自动化契约测试

- 所有关键静态控件 AutomationId 唯一且跨布局稳定。
- 可访问名称为中文用途描述。
- 动态列表项可按固定测试文件名搜索，不依赖数据库随机 ID。
- Invoke、Toggle、Value、Selection 和 Window 模式与控件行为一致。
- UIA 驱动在发布窗口中能发现并操作契约要求的控件。

### 15.3 编排器测试

- 工具锁定清单、版本和 SHA-256 校验。
- 预检阻塞不启动或终止用户实例。
- 临时根创建、所有权、重解析点拒绝和安全清理。
- 环境变量只进入被测子进程。
- 观察型等待可重试，有副作用的动作不重放。
- 超时、截图、UIA 树、报告和脱敏日志输出。
- 成功、失败、脚本异常和用户中断后的进程与目录零残留。

### 15.4 发布窗口场景

- 设置与目录保存。
- 扫描和发现。
- 单个及批量资料。
- MP4/M4A 前置处理与完成后资料栏刷新。
- 入库和目标冲突。
- 正式文件库组合筛选、批量维护与撤销。
- 词表新增、编辑、合并和删除边界。
- 系统诊断。
- 响应式、主题、键盘和单实例。

### 15.5 回归

- 当前 970 项测试为最低回归基线，Stage 5C-C 新测试叠加其上。
- Stage 1 至 Stage 5C-B 的扫描、前置处理、入库、恢复、批量编辑、命名、词表、诊断、单实例和离线启动保持通过。
- Release 构建必须零错误、零警告。
- 既有包级 smoke、诊断探针和清理检查继续通过。

## 17. 人工补充验收

自动化完成后，人工清单只保留系统边界和视觉判断：

1. 双击验收入口后不会一闪而过，最终摘要和报告路径清晰。
2. `1024×720`、`1280×800` 和宽屏截图的层级、密度和留白合理。
3. 明暗主题均无难以辨认的文字、图标、选中态或状态提示。
4. 紧凑模式资料抽屉符合直觉，Esc 和关闭按钮返回正确焦点。
5. Windows 文件夹选择器能选目录并安全返回 TraceFold。
6. “打开日志目录”等系统入口只打开已注册位置。
7. 系统剪贴板复制行为正常，脱敏内容符合 Stage 5C-B 约束。
8. 应用图标、任务栏、窗口标题、原生窗口行为和关闭体验正常。
9. 产品包中不存在自动化工具、脚本或测试媒体。
10. 验收后系统中无残留测试进程和测试目录。

全新 Windows 11 x64 机器验证在具备条件时执行并单独记录。当前缺少虚拟机不会将本阶段人工结果虚报为已经完成干净机器验证。

## 18. 完成标准

Stage 5C-C 只有同时满足以下条件才可进入最终人工验收：

1. 资源管理器式三栏和既有业务操作逻辑保持不变。
2. `>=1280` 使用完整三栏，`1024–1279` 使用紧凑导航和资料抽屉。
3. `1024×720` 下关键内容、应用自有对话框和主要动作无不可达裁切。
4. 明暗主题、38 px 文件行、间距、按钮和状态表达由统一语义资源控制。
5. 布局切换不丢失页面、选择、筛选、搜索或编辑草稿。
6. 关键控件的 AutomationId、可访问名称、UIA Pattern 和焦点路径稳定。
7. 独立验收工具包可离线、一键运行且无需安装外部服务。
8. 端到端场景驱动真实发布程序，不使用测试业务后门。
9. 所有场景使用独立拥有的数据根且不接触用户数据。
10. 每个业务步骤同时验证界面和持久化或文件事实。
11. 失败证据完整、日志脱敏、有副作用的动作不自动重放。
12. 验收结束后无本次运行拥有的 TraceFold、FFmpeg、FFprobe 进程或临时测试数据残留。
13. 全量测试在 970 项基线上继续增长并全部通过；Release 构建零错误、零警告。
14. 产品包 smoke、诊断探针、UI 自动化、报告与视觉截图索引全部通过。
15. 产品包与自动化工具包严格分离并各自提供 SHA-256、版本和源提交证据。
16. 人工补充清单由用户实际执行并报告；全新机器结果未执行时保持明确标记。

## 19. 实施顺序约束

后续实施计划必须遵循以下顺序：

1. 先用测试固定视觉资源键、AutomationId、可访问名称和 UIA Pattern 契约。
2. 再建立集中视觉资源，并逐页迁移硬编码值；不得一开始同时重写全部页面逻辑。
3. 实现 Shell 响应式状态、资料抽屉、焦点恢复和最低窗口行为。
4. 补齐真实运行时 UIA 可发现性，只有平台默认能力不足时增加 AutomationPeer。
5. 建立工具锁定清单、隔离根、所有权、预检、进程跟踪和清理基础设施。
6. 先完成无业务副作用的启动、导航、布局、主题和诊断场景，再加入扫描、处理、入库等有副作用场景。
7. 每加入一个业务场景，同时加入界面断言、事实断言、超时、失败证据和清理测试。
8. 最后生成独立产品包、独立验收工具包、人工指南和哈希证据。
9. 每个纵向任务以红—绿—重构执行，并形成可独立审查的提交。

本规格没有遗留产品选择。实现中的具体类型和文件名称可以遵循仓库现有惯例，但不得削弱产品包与工具包隔离、真实发布窗口驱动、用户数据隔离、所有权校验、有副作用动作不重放、响应式焦点恢复或无残留清理约束。
