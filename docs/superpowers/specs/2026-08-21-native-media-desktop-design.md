# TraceFold 原生媒体桌面端设计

- 日期：2026-08-21
- 状态：聊天设计已确认，待规格审阅
- 目标平台：Windows 11 x64
- 技术路线：.NET 10 LTS、WinUI 3、Windows App SDK、SQLite

## 1. 背景与决策

当前媒体文件库已经通过 `apps/media-api` 与 `apps/media-web` 实现了扫描、标注、前置处理、冲突处理和正式入库等核心能力，但测试包仍以浏览器应用模式运行。仓库中的 `apps/desktop` 只是旧 TraceFold 工作台的 Python 桌面壳骨架，实际仍调用浏览器，既不是原生业务客户端，也不属于新的媒体文件库边界。

本次不再给现有 Web 界面增加宿主，而是平行建设 Windows 原生媒体客户端。新客户端使用 WinUI 3 实现界面，并用 .NET 重新实现业务和基础设施层。Python、FastAPI、React 和旧 SQLite 数据库只作为现有行为的参考，不成为新客户端的运行依赖。

迁移期保留 Web 版，原生版逐项达到功能对齐后再退役 Web 版。两套客户端在并行期间使用不同的数据库、待入库目录、正式库目录和工作目录，禁止同时操作同一批文件。

新客户端建立空数据库，不迁移旧业务数据。旧数据库保持不动并可用于回看；旧正式库中的登记数据不会自动导入新客户端。

## 2. 产品目标

原生客户端完整覆盖媒体文件从下载完成到正式文件库的主要流程：

1. 扫描用户指定的待入库目录。
2. 等待下载文件稳定，避免处理仍在写入的内容。
3. 检测并执行可扩展的前置处理；首个处理器合并同名 MP4 与 M4A。
4. 预览图片或视频，编辑显示名称、作者、系列和内容标签。
5. 通过安全、可恢复的事务将媒体移动到正式文件夹。
6. 在图库中搜索、筛选和编辑正式资产的显示资料。

产品仍以“方便管理文件”为首要目标。普通文件的日常路径保持为：

> 刷新 → 选择 → 标注 → 正式入库

后台处理、事务日志和恢复能力不暴露为复杂的任务管理产品。

## 3. 首版范围

### 3.1 包含

- 真正的独立 Windows EXE 和原生软件窗口。
- 待入库、正式文件库、词表管理和设置四个主模块。
- 图片与视频共用同一元数据模型。
- 一个媒体可有多位作者、零或一个系列、多个内容标签。
- 物理文件默认保持原文件名。
- 显示名称独立存储，编辑显示名称不修改物理文件名。
- 手动刷新与定时自动扫描。
- 普通图片和普通视频直接入库。
- 可扩展前置处理框架，以及同名 MP4/M4A 合并处理器。
- 名称或内容冲突时的原生对比弹窗。
- 跳过、两者都保留、替换三种冲突处理方式。
- 正式库的名称搜索、媒体类型和元数据组合筛选。
- 批量追加作者、批量追加标签和批量替换系列。
- 单实例、后台处理、异常退出恢复、本地日志和离线测试包。

### 3.2 不包含

- 旧数据库或旧业务资料迁移。
- Python、FastAPI、React 或浏览器运行依赖。
- 外部 DLL 插件加载、插件市场或第三方脚本执行。
- 网络下载器、浏览器抓取、云同步和远程访问。
- AI 自动识别、自动标签或内容推荐。
- 多用户、权限和远程数据库。
- 多窗口、标签页、托盘、开机启动、安装器和自动更新。
- 修改正式媒体的物理文件名。
- 按作者、系列或标签创建物理子目录。
- macOS、Linux、x86 或 ARM64 支持。

## 4. 技术选型

### 4.1 采用 WinUI 3 + .NET 10

新客户端采用 .NET 10 LTS、WinUI 3 和 Windows App SDK。选择理由：

- 目标明确为新的 Windows 原生客户端，而非跨平台应用。
- WinUI 3 是微软面向新 Windows 原生应用的当前推荐界面框架。
- Fluent 控件、窗口生命周期和 Windows 系统能力符合预期体验。
- .NET 10 是当前活跃 LTS，可为完整重构提供稳定生命周期。

### 4.2 未采用路线

- **WPF**：生态成熟、工程风险较低，但默认体验较传统，新项目需要额外投入才能达到现代 Windows 视觉和窗口行为。
- **Avalonia**：适合跨平台，但使用自有渲染体系；当前没有跨平台目标，引入它只会扩大依赖和测试矩阵。
- **WebView2、Tauri、Electron、pywebview**：都会继续以 Web 页面作为主要业务界面，与“主要功能逐步原生化并重写后端”的已确认方向不符。

## 5. 代码与组件架构

新应用放在独立目录，不改造旧 `apps/desktop`：

```text
apps/media-desktop/
  TraceFold.MediaDesktop.slnx
  src/
    TraceFold.Media.Desktop/
    TraceFold.Media.Application/
    TraceFold.Media.Domain/
    TraceFold.Media.Infrastructure/
  tests/
    TraceFold.Media.Domain.Tests/
    TraceFold.Media.Application.Tests/
    TraceFold.Media.Infrastructure.Tests/
    TraceFold.Media.Desktop.Tests/
```

### 5.1 `TraceFold.Media.Desktop`

负责 WinUI 3 窗口、页面、对话框、控件、ViewModel、导航、Windows 文件选择器、原生图片预览、视频播放和系统外壳交互。它也是依赖注入和应用启动的组合根。

ViewModel 只能调用应用层命令和查询，不能直接访问 EF Core、SQLite、文件系统、FFmpeg 或进程 API。界面依据应用层返回的状态和允许动作显示按钮，不能在前端复制状态机规则。

### 5.2 `TraceFold.Media.Application`

负责用户用例和流程编排，包括扫描、处理、保存草稿、批量标注、入库、冲突解决、重试、查询、词表维护和设置修改。

应用层定义数据库仓储、文件存储、媒体探测、处理执行、时间和事件通知等端口。它依赖领域层，不依赖 WinUI 或具体基础设施。

### 5.3 `TraceFold.Media.Domain`

负责实体、值对象、状态迁移、元数据约束、冲突策略、处理器契约和入库规则。该项目不引用 WinUI、EF Core、SQLite、Windows App SDK 或 FFmpeg。

所有有效状态迁移和 `AllowedActions` 都由领域对象或领域策略产生。调用者不能绕过领域规则直接写状态字符串。

### 5.4 `TraceFold.Media.Infrastructure`

负责 EF Core SQLite、迁移、文件系统、哈希、缩略图、媒体探测、FFmpeg 子进程、日志、后台任务执行器和启动恢复。它实现应用层定义的端口。

只有存储实现可以移动或删除媒体文件。处理器只能在工作目录读取输入、生成输出并验证结果，不能删除源文件或直接写入正式库。

### 5.5 依赖方向

```text
Desktop → Application → Domain
Desktop → Infrastructure → Application / Domain
```

`Domain` 不依赖其他项目。`Application` 不依赖 `Desktop` 或 `Infrastructure`。具体实现通过依赖注入连接，避免界面、业务规则和文件操作再次混在同一模块。

新客户端在进程内调用应用服务，不启动本地 HTTP 服务，也不保留第二套 API DTO。后台任务通过进程内调度和持久化任务记录协作。

## 6. 主窗口与交互

主窗口采用已确认的“资源管理器式三栏”布局：

- **左侧导航**：待入库、正式文件库、词表管理、设置。
- **中间内容区**：媒体图库、搜索、筛选、刷新和多选。
- **右侧资料面板**：预览、显示名称、作者、系列、标签和当前主操作。

单选媒体时，右侧展示完整资料；多选时切换为批量标注。批量作者和标签操作为追加，批量系列操作为替换，并明确提示单系列语义。

处理进度、失败和冲突状态直接显示在媒体卡片和资料面板上，不增加独立任务中心。图片使用原生图片控件，视频使用 WinUI 媒体播放器。正式资产提供“打开所在目录”，但调用只接受已经登记的资产标识，不接受任意外部路径。

冲突不是常驻页面。只有用户发起入库且准备阶段检测到冲突时，才显示原生模态对比窗口，左右展示库内文件和待入库文件的预览、实际文件名、大小、时间、媒体信息和已有元数据。

主窗口关闭即退出整个程序，不进入托盘。首版只有一个主窗口，不增加多窗口工作区。

## 7. 数据模型

### 7.1 核心实体

- `InboxItem`：一次待入库工作单元，可关联一个或多个源文件。
- `SourceFile`：源文件规范路径、扩展名、大小、修改时间、轻量指纹、完整哈希和存在状态。
- `MetadataDraft`：显示名称、多作者、零或一个系列和多标签。
- `ProcessingPlan`：处理器版本、步骤顺序、输入和预期输出。
- `ProcessingJob`：任务状态、尝试次数、当前步骤、输出、错误和恢复信息。
- `MediaAsset`：正式媒体的逻辑记录，包括媒体类型、实际文件名、正式相对路径、显示名称、大小、哈希和预览信息。
- `Author`、`Series`、`Tag`：独立词表。
- `IngestOperation`：准备、提交和清理三个阶段的持久化操作日志。
- `ConflictCase`：冲突双方快照、目标名称、哈希、用户选择和选择有效性。

### 7.2 关系与名称语义

- `InboxItem` 与 `SourceFile`：一对多。
- `InboxItem` 与 `ProcessingJob`：一对多。
- `MediaAsset` 与 `Author`：多对多。
- `MediaAsset` 与 `Tag`：多对多。
- `MediaAsset` 与 `Series`：可选多对一。

`actual_filename` 是正式目录中的真实文件名，入库后只读。`display_name` 是可编辑的逻辑名称；界面优先显示它，为空时回退到真实文件名。MP4/M4A 合并结果沿用 MP4 基本名称和 `.mp4` 扩展名。

词表名称以去除首尾空白后的规范值判重，并保留展示形式。图片和视频共享同一资产与元数据关系，不建立两套作者、系列或标签模型。

## 8. 待入库状态与扫描

领域状态机为：

```text
Discovered
  → WaitingForStability
  → Analyzing
  → Processing（需要前置处理时）
  → ReadyToTag
  → Ingesting
  → Conflict（检测到冲突时）
  → Ingesting
  → Completed

任意分析、处理或入库阶段 → Failed
Failed → 对应的安全重试点
Conflict → ReadyToTag（跳过）| Ingesting（保留两者或替换）
ReadyToTag → Analyzing（源文件变化或发现新的伴随文件）
```

扫描器同时服务手动刷新和定时扫描，两者调用同一个幂等用例。系统忽略 `.part`、`.crdownload` 等已知临时文件。候选文件至少连续两次观察到大小和修改时间不变后，才允许分析、处理或入库。

扫描器只负责发现稳定候选，不包含 MP4/M4A 等格式分支。配对和适用性判断属于处理器。

## 9. 可扩展前置处理

每个内置处理器实现统一契约，至少声明：唯一名称、版本、支持输入、适用性检测、计划生成、执行步骤、输出验证、资源需求、自动执行安全性和错误分类。

处理器通过 .NET 依赖注入显式注册。新增内置处理器只需增加实现并注册，不修改扫描器、入库服务或界面主流程。首版不动态加载外部 DLL，避免不可信代码、版本冲突和离线分发复杂度。

计划器根据显式优先级和依赖关系生成有序步骤。持久化后台执行器从 SQLite 领取任务，保存步骤和诊断信息，并在启动时恢复排队或中断任务。

首个 `mp4_m4a_merge` 处理器：

1. 检测同一目录、同基本名称的 `.mp4` 与 `.m4a`。
2. 在工作目录调用随包提供的 FFmpeg 生成临时 MP4。
3. 使用 FFprobe 验证输出包含可用视频流与音频流。
4. 将验证后的输出交给入库流程。
5. 不覆盖或删除输入文件。

一个任务失败只影响对应 `InboxItem`。失败记录包含稳定错误代码、可重试标记、用户提示和日志关联标识。

## 10. 正式入库与冲突

文件系统和 SQLite 无法共享真正的原子事务，因此通过持久化 `IngestOperation` 和可恢复的三阶段协议保证一致性。

### 10.1 Prepare

1. 验证源文件或处理输出仍存在且未变化。
2. 验证元数据关系和当前状态。
3. 计算最终输入完整哈希。
4. 计算目标名称并检测名称或内容冲突。
5. 检查空间后复制到工作区暂存目录。
6. 验证暂存文件的大小、哈希和可读性。
7. 在任何正式文件移动前持久化操作日志。

### 10.2 Commit

1. 将暂存文件移动到正式目标位置。
2. 在 SQLite 事务中创建或更新 `MediaAsset`、写入关系、完成 `InboxItem` 并标记操作已提交。

如果文件移动成功但数据库提交失败，启动恢复根据操作标识、记录路径和哈希完成提交或安全退回暂存区，不能只凭文件名判断。

### 10.3 Cleanup

提交完成并重新验证后，统一清理服务才能删除普通入库源文件、合并场景中的原 MP4 与 M4A、处理输出、暂存文件和替换备份。清理失败不会撤销已成功入库的资产，而是留下可重试清理记录。

### 10.4 冲突选择

- **跳过**：保留源文件，项目返回 `ReadyToTag`。
- **两者都保留**：使用 `name (2).ext`、`name (3).ext` 等下一个可用真实名称；显示名称不自动加后缀。
- **替换**：先把旧文件和旧元数据放入本次操作的可恢复备份，再提交新文件；验证成功后才清理备份。

冲突选择绑定源哈希和目标名称。源文件变化后，旧选择失效并重新提示。

## 11. 生命周期、并发与错误处理

启动顺序：

1. 获取应用级单实例锁；重复启动时激活现有窗口。
2. 打开新客户端自己的 SQLite 并执行结构迁移。
3. 加载目录与处理器设置，验证路径安全性。
4. 恢复中断的处理和入库操作。
5. 启动扫描与后台执行器。
6. 恢复完成前允许浏览，暂时禁用新入库提交。

目录路径必须规范化。待入库、正式库和工作目录不能相同，也不能形成会递归扫描或把暂存内容当成新输入的危险包含关系。

耗时操作只在后台执行。界面线程通过应用事件更新状态。重复点击、重试和窗口刷新必须保持幂等，不能创建重复任务或重复资产。

关闭顺序：停止接受新任务，通知后台操作在安全检查点结束，终止仍运行的 FFmpeg 子进程，持久化中断状态，然后退出。下次启动从任务和操作日志恢复。

用户可处理的问题显示在卡片或右侧资料面板；需要用户决定的问题使用原生弹窗；程序级故障使用顶部通知并写本地日志。日志按操作关联标识串联扫描、处理、文件操作和数据库提交，不记录媒体内容。

## 12. 本地数据与设置

首版固定使用以下应用数据根目录：

```text
%LocalAppData%\TraceFold\MediaDesktop\
```

其中存放新 SQLite 数据库、日志、恢复状态和默认工作目录。待入库目录和正式库目录由用户设置。数据库总是属于原生客户端，不允许配置为旧 Web 数据库。

首次启动创建空数据库并进入目录设置引导。未完成安全目录配置前，应用可以启动和打开设置页，但不能扫描或入库。

并行验收期间，原生客户端必须使用测试目录或真实文件副本。Web 版继续操作原目录。正式切换时先停止 Web 版，再明确配置原生客户端目录；本设计不自动转换旧资产记录或扫描旧正式库建立数据库。

## 13. 测试策略

### 13.1 领域与应用测试

- 状态迁移和 `AllowedActions`。
- 多作者、单系列、多标签约束。
- 文件稳定性、扫描幂等和源变化失效。
- 处理器适用性、计划顺序和版本记录。
- 冲突后缀、三种选择和选择失效。
- 取消、重试、重复命令和批量操作语义。

### 13.2 基础设施集成测试

使用临时 SQLite、临时目录和仓库内固定小型媒体样本覆盖：

- 普通图片和视频完整入库。
- MP4/M4A 合并、流验证和提交后源文件清理。
- Prepare、Commit、Cleanup 各阶段故障注入。
- 文件移动成功但数据库提交失败。
- 清理失败后的启动重试。
- 名称冲突、内容冲突和替换恢复。
- 路径包含、空间不足、权限不足和源文件变化。

测试不下载网络资源。真实 FFmpeg 测试使用可再分发的固定样本。

### 13.3 桌面界面与验收

ViewModel 在不启动窗口的情况下进行单元测试。WinUI 控件设置稳定 `AutomationId`，关键流程通过 Windows UI Automation 驱动。自动化驱动被封装在测试基础设施中，避免测试业务依赖某个桌面自动化工具的内部 API。

每个实施阶段都生成可启动构建，并执行独立窗口、导航、关闭退出和错误展示烟雾测试。最终离线包使用真实文件副本手动验收视频播放、冲突左右预览、资源管理器定位和异常退出恢复。

## 14. 离线测试包

首份测试包面向 Windows 11 x64，以 ZIP 文件交付。解压后点击 `TraceFold.Media.exe` 打开独立窗口。测试包：

- 自带 .NET 10 运行时。
- 使用 Windows App SDK 自包含部署。
- 包含 FFmpeg、FFprobe 及相应许可证文件。
- 不联网、不打开浏览器、不显示常驻命令行窗口。
- 不包含安装器、自动更新、托盘和开机启动。

发布验证必须在未安装开发工具的干净 Windows 11 x64 环境中完成，不能把本机 SDK、Visual Studio 或环境变量当作隐藏依赖。

## 15. 实施分期

完整功能对齐是同一产品目标，但实施拆成可单独验收的纵向切片。每个切片通过验收后再进入下一切片。

### 阶段 1：原生基础

建立解决方案、四层项目、WinUI 主窗口、依赖注入、空数据库、设置、日志、单实例和关闭生命周期。此阶段不移动真实媒体文件。

### 阶段 2：普通文件入库闭环

实现扫描、稳定性判断、图片和视频预览、元数据草稿、词表、普通文件入库和正式库浏览，形成第一个可用纵向切片。

### 阶段 3：可扩展前置处理

实现处理器契约、注册、计划器、持久化执行器、FFmpeg/FFprobe 封装和 MP4/M4A 合并。

### 阶段 4：冲突与恢复

实现三阶段入库、原生冲突对比弹窗、三种选择、故障注入、启动恢复和延迟清理。

### 阶段 5：完整功能对齐

实现批量标注、组合筛选、词表管理、设置诊断、UI Automation、视觉细节和完整离线测试包。

### 阶段 6：切换与退役

使用真实文件副本逐项对照 Web 版验收。通过后冻结旧版、切换正式入口和目录。旧应用删除或归档属于后续独立变更，不混入原生客户端实现提交。

该项目规模不适合一个巨型实现计划。总体规格确认后，先为“阶段 1：原生基础”编写独立实施计划；后续阶段各自经过规格核对、计划和验收。

## 16. 验收标准

1. 点击 `TraceFold.Media.exe` 打开原生窗口，不出现浏览器或常驻命令行。
2. 重复启动不会产生两个同时操作数据库和文件夹的进程。
3. 用户可以配置安全隔离的待入库、正式库和工作目录。
4. 下载完成并稳定的图片和视频只被发现一次。
5. 用户可以设置多作者、零或一个系列、多标签和可选显示名称。
6. 普通文件入库后位于正式目录，默认物理文件名不变。
7. 同名 MP4/M4A 经过可扩展处理框架合并并验证音视频流。
8. 合并入库提交成功后原 MP4 和 M4A 被清理；失败时源文件仍保留。
9. 名称或内容冲突必须展示双方预览，并按用户选择跳过、保留两者或替换。
10. 正式库可按名称、作者、系列、标签和媒体类型检索。
11. 修改显示名称不会修改物理文件名。
12. 在处理或入库任意阶段终止并重启，不会丢失源文件、重复资产或留下无法解释的正式文件。
13. 一个媒体失败不会阻塞其他媒体继续扫描、标注和入库。
14. 关闭主窗口后客户端和其 FFmpeg 子进程全部退出。
15. 离线包在干净 Windows 11 x64 环境中无需安装开发工具即可运行。

## 17. 风险与控制

- **完整重写导致范围过大**：通过六个纵向切片、逐阶段规格与验收控制。
- **新界面再次承载业务逻辑**：通过四层依赖规则、应用用例和领域状态机控制。
- **文件丢失或数据库与文件不一致**：通过单一存储边界、三阶段入库、哈希、操作日志和提交后清理控制。
- **处理器扩展重新变成格式条件分支**：通过处理器契约、显式注册和统一计划器控制。
- **WinUI 部署在开发机可用但测试机失败**：通过 Windows App SDK 自包含包和干净环境验证控制。
- **Web 与原生客户端争用文件**：通过独立目录、独立数据库和明确切换步骤控制。
- **过早删除现有可用版本**：原生版完整验收前保持 Web 版和旧数据库不变。

本规格定义原生媒体客户端的总体目标和长期边界。下一步仅为阶段 1 编写实施计划，不直接展开全部六个阶段的代码工作。
