## 1. 目标

Stage 4 在已验收的扫描、资料标注、预览、安全入库和可扩展前置处理闭环上，补齐正式入库时的冲突决策与崩溃恢复能力。

冲突与恢复规则同时适用于当前已经支持入库的图片和视频；本阶段不借此扩展媒体格式范围。

面向用户的主路径保持不变：

> 刷新 → 可选前置处理 → 标注资料 → 正式入库

只有发现冲突时才增加一个明确的决策步骤：

> 正式入库 → 对比冲突 → 跳过 / 保留两者 / 替换 → 安全入库

本阶段不建立第二套冲突入库流程。冲突决策完成并重新验证后，仍然进入现有的三阶段入库状态机。替换操作增加受控备份和恢复证据，但不绕过既有的暂存、提交与清理边界。

## 2. 验收拆分

Stage 4 是一份统一设计，分为两个连续验收点：

### 2.1 Stage 4A：冲突处理闭环

- 持久化名称冲突和内容冲突。
- 原生对比弹窗。
- 跳过、保留两者和替换。
- 多个内容匹配项的目标选择。
- 用户关闭弹窗后保留待处理状态。
- 决策提交前重新验证。
- 替换前建立基础受控备份，保证正常执行和普通 I/O 失败时不会直接覆盖旧文件。

4A 是功能验收包，不代表替换流程已经完成全部进程终止恢复保证。

### 2.2 Stage 4B：恢复加固

- 替换备份的完整持久化生命周期。
- 扩展 `IngestOperation` 的恢复证据。
- 启动时安全恢复。
- 测试专用故障注入。
- 延迟清理、有限退避和手动重试。
- 覆盖替换、保留两者和多来源前置处理结果的崩溃恢复。

Stage 4 只有在 4B 通过后才视为整体完成。

## 3. 已确认的产品决策

1. 冲突弹窗关闭或按 `Esc` 不代表作出选择；项目保持 `ConflictBlocked`，右侧详情栏可以重新打开弹窗。
2. “保留两者”创建两个独立正式文件和两个独立资产记录。内容哈希允许重复，但继续用于检测和提示。
3. “保留两者”的实际文件名使用 `名称 (2).扩展名`、`名称 (3).扩展名`；用户设置的显示名称不变。
4. 替换已登记资产时保留既有资产 ID 和正式实际文件名，文件内容和全部资料改为待入库项目的数据。
5. 被替换的旧文件和旧资料必须进入可恢复备份。
6. 正式文件夹内存在同名但未登记的文件时，同样显示对比并允许跳过、保留两者和替换；替换前先备份未登记文件。
7. 启动恢复只自动执行能够由操作 ID、受控路径、大小和哈希共同证明安全的动作；状态含糊时停止并交由用户检查。
8. 不增加独立恢复中心。恢复状态和操作入口位于对应项目的右侧详情栏。
9. 清理失败不阻塞其他文件；后台有限退避重试，并提供“立即重试”。
10. 冲突使用持久化 `ConflictCase` 表达，用户作出选择后恢复同一个既有三阶段入库管线。
11. 存在多个同内容匹配项时，名称冲突优先以同名目标作为替换目标；只有内容冲突时由用户明确选择一个目标。
12. “替换”始终只影响一个明确目标，不会自动替换全部同内容资产。

## 4. 范围

### 4.1 包含

- 名称、内容和组合冲突的持久化模型。
- 已登记资产和未登记正式文件的冲突匹配项。
- 受控预览与对比 DTO。
- 跳过、保留两者和替换的应用用例。
- 多内容匹配项的目标选择。
- 冲突重新验证、失效和重新扫描。
- 重复内容资产的数据迁移和非唯一哈希索引。
- 操作级备份、恢复快照和受控恢复目录。
- 正常异常回滚、启动恢复和恢复阻塞状态。
- 延迟清理工作器和手动重试。
- 测试专用故障注入。
- 4A、4B 两份离线 Windows x64 测试包和人工验收清单。

### 4.2 不包含

- 批量冲突处理、批量标注和批量入库。
- 高级筛选、组合搜索和保存筛选条件。
- 独立任务中心或恢复中心。
- 版本历史浏览、长期保留旧版本和用户主动回滚。
- 用户自定义重名模板。
- 外部插件、脚本或联网服务。
- Stage 5 的完整桌面 UI 自动化框架。

## 5. 架构选择

采用“持久化冲突案例 + 用户决策 + 恢复既有入库状态机”：

```text
请求正式入库
  → 计算有效输入快照并检测冲突
  → 持久化 ConflictCase 与所有匹配项
  → 原生对比弹窗
  → 持久化用户决策
  → 重新验证输入与目标
  → 创建或恢复 IngestOperation
  → Stage → File Commit → Database Commit → Cleanup
```

替换只在既有管线中增加备份子步骤：

```text
Stage → Backup Target → Commit File → Commit Database → Verify → Cleanup
```

没有采用以下方案：

- 仅在 ViewModel 中保存一次性选择：实现较短，但关闭窗口、重启或外部文件变化后无法可靠恢复决策。
- 为冲突建立一套平行入库管线：会复制暂存、提交、清理和恢复逻辑，扩大状态组合并造成长期分叉。

依赖方向继续保持：

```text
Desktop → Application → Domain
Desktop → Infrastructure → Application / Domain
```

Desktop 只消费对比 DTO 和允许执行的动作，不包含路径选择、哈希判断、覆盖或重命名规则。

## 6. 领域模型

### 6.1 ConflictCase

`ConflictCase` 表示一次可持久恢复的冲突判断，至少包含：

- 案例 ID 和待入库项目 ID。
- 有效输入文件标识、大小、修改信息和 SHA-256。
- 原始目标文件名和检测时的资料版本。
- 一个或多个 `ConflictMatch`。
- 用户选择的 `ConflictResolution`。
- 选择的替换目标；不替换时为空。
- 创建、更新和解决时间。
- 失效或失败原因。

建议状态：

```text
Open → Chosen → Resolved
  └──────────→ Invalidated
  └──────────→ Skipped
```

- `Open`：等待用户处理，也对应界面的 `ConflictBlocked`。
- `Chosen`：选择已持久化，正在重新验证或等待入库操作接管。
- `Resolved`：选择已由入库操作安全落实。
- `Invalidated`：输入或目标变化，原选择不得再执行。
- `Skipped`：用户明确跳过，本次案例结束但源文件保留。

状态名可在实施时贴合现有命名，但含义和转换约束不得弱化。

### 6.2 ConflictMatch

每个匹配项保存检测时的稳定快照：

- 匹配项 ID 和冲突案例 ID。
- 匹配原因：名称、内容或两者都有。
- 是否为已登记资产。
- 已登记时的资产 ID 和并发版本。
- 受控目标路径标识，不向桌面层暴露任意路径访问能力。
- 实际文件名、显示名称、大小、修改时间和哈希。
- 媒体类型、格式、分辨率、时长等可用属性。
- 作者、系列和内容标签快照。
- 预览引用或安全的占位状态。

内容相同可以产生多个匹配项。匹配项集合不是替换清单；替换仍必须选定单个目标。

### 6.3 ConflictResolution

```text
Skip | KeepBoth | Replace
```

允许的动作由应用层根据案例和匹配项生成。Desktop 不自行推断何时允许替换。

### 6.4 IngestOperation 扩展

现有 `IngestOperation` 继续作为唯一入库状态机，并增加：

- 关联的冲突案例 ID。
- 已确认的冲突策略。
- 最终目标路径标识和预期哈希。
- 替换资产 ID 或未登记目标快照。
- 新资料的不可变提交快照。
- 旧资产和关系的恢复快照。
- 备份位置、旧哈希和备份状态。
- 每个文件系统提交点的恢复证据。
- 恢复阻塞原因。

主要状态继续沿用：

```text
Created → Staged → FileCommitted → DatabaseCommitted
        → CleanupPending → Completed
```

恢复无法安全自动推进时进入 `RecoveryBlocked`。备份状态作为操作的附属状态表达：

```text
NotRequired | Pending | Created | Restored | Deleted
```

## 7. Stage 4A 冲突处理流程

### 7.1 检测时机和有效输入

用户点击“正式入库”后，应用层先解析最终有效输入：

- 普通项目使用原始媒体文件。
- 已成功完成前置处理的项目使用处理输出参与冲突检测和后续提交。
- 前置处理来源仍作为清理清单保留，不能由冲突检测或处理器删除。

应用层计算不可变输入快照，然后检测：

- 计划使用的实际文件名是否已存在。
- 是否存在一个或多个相同内容哈希的已登记资产。
- 同名目标是否为正式文件夹中的未登记文件。
- 名称冲突和内容冲突是否同时存在。

一旦发现冲突，先持久化案例与全部匹配项，然后返回案例 ID。此时不暂存、不移动、不覆盖正式文件。

### 7.2 对比弹窗

弹窗左侧显示待入库项目，右侧显示冲突匹配项。信息包括：

- 预览图或安全占位图。
- 实际文件名和显示名称。
- 文件大小、修改时间、格式、分辨率和时长等可用属性。
- 作者、系列和内容标签。
- 是否已经登记为正式资产。
- 名称冲突、内容相同等冲突原因。

所有预览和文件信息由应用层通过受控服务生成。预览失败只显示占位图，不阻止用户处理冲突。

有多个匹配项时：

- 存在同名目标则默认选中同名目标。
- 只有内容冲突时，必须由用户明确选中一个目标后才能替换。
- 跳过和保留两者不要求选择替换目标。
- 替换按钮始终只对应当前单个目标。

关闭弹窗或按 `Esc` 不提交决策。案例保持 `Open`，项目保持 `ConflictBlocked`，右侧详情栏显示“处理冲突”。

### 7.3 跳过

用户明确选择跳过后：

- 案例标记为 `Skipped`。
- 项目返回可编辑、可再次请求入库的状态。
- 待入库源文件、前置处理来源和处理输出全部保留。
- 正式文件和数据库均不变化。

### 7.4 保留两者

用户选择保留两者后：

- 创建新的正式文件和新的资产记录。
- 冲突弹窗显示预计实际文件名。
- 重名文件使用 `名称 (2).扩展名`、`名称 (3).扩展名`，序号从第一个可用值开始。
- 正式提交门内再次检查目标名。如果外部进程刚占用了预计名称，自动推进到下一个可用序号，不重复弹窗。
- 显示名称和资料快照不因实际文件名后缀而改变。
- 相同哈希允许入库为独立资产。

后缀选择必须位于受控存储提交边界中，不能由 ViewModel 先判断后直接写文件。

### 7.5 替换已登记资产

- 保留既有资产 ID。
- 保留目标的正式实际文件名。
- 文件内容替换为待入库有效输入。
- 显示名称、作者、系列和内容标签全部替换为待入库项目的提交快照。
- 旧文件、旧资产字段和旧关系快照进入操作级恢复备份。
- 备份和新文件验证成功前不修改资产资料。

一个资产仍然最多属于一个系列；作者和内容标签继续支持多值。

### 7.6 替换未登记文件

- 先为未登记目标建立受控文件备份并验证哈希。
- 待入库文件使用被替换目标的实际文件名。
- 创建新的资产 ID 和资料关系。
- 数据库提交失败时可以恢复原未登记文件。

### 7.7 决策提交前重新验证

用户作出选择后，应用层必须再次验证：

- 有效输入仍然存在，大小和哈希未变化。
- 前置处理输出及其来源关系仍然有效。
- 被选目标仍然存在，大小、哈希和登记状态未变化。
- 已登记目标的资产并发版本未变化。
- 当前资料可以固化为本次操作的提交快照。

如果输入或目标发生变化：

- 原案例标记为 `Invalidated`。
- 不执行旧选择，也不把“替换”静默降级为新建。
- 重新扫描冲突。
- 仍有冲突时创建或刷新新的案例。
- 冲突已经消失时返回可入库状态，并提示用户重新确认正式入库。

## 8. Stage 4B 受控提交与备份

### 8.1 文件系统边界

正式文件库内设置由存储适配器独占管理的内部恢复区域，例如：

```text
<library>/.tracefold/recovery/<operation-id>/
<library>/.tracefold/commit/<operation-id>/
```

实际命名可在实施时按 Windows 路径规则调整，但必须满足：

- 不参与正式媒体扫描和冲突匹配。
- 不显示为资产。
- 每个操作独立，不能共享可写文件。
- 最终重命名发生在正式文件同一卷上，尽可能使用原子移动。
- 跨卷输入先复制到正式库内部提交区并校验，再执行同卷提交。
- 所有路径仍需经过现有受控根目录和防越界检查。

### 8.2 替换顺序

1. 创建或恢复唯一的 `IngestOperation`。
2. 持久化输入、目标、资料、旧资产和来源清单快照。
3. 暂存输入并验证大小和 SHA-256。
4. 将旧目标移动到操作独占的恢复目录。
5. 验证备份哈希并持久化 `BackupState.Created`。
6. 将新文件提交到目标位置并验证预期哈希。
7. 在数据库事务中更新原资产或创建新资产。
8. 验证目标文件、数据库记录和操作 ID 一致。
9. 进入 `CleanupPending`，依次清理来源、临时提交文件和备份。

任何可能改变正式文件的动作之前，数据库都必须已经保存完成该动作或撤销该动作所需的证据。

### 8.3 数据不丢失不变量

- 备份前，旧目标是有效副本。
- 旧目标移走后，已验证备份是有效副本。
- 新目标提交后，新目标和备份同时保留。
- 数据库提交和最终一致性验证完成前不得删除备份。
- 输入来源只在正式文件与数据库均验证成功后进入清理。
- 无法证明下一步安全时不移动、不覆盖、不删除任何文件。

保留两者不需要目标备份，但仍使用相同的暂存、提交、数据库提交和清理状态。

## 9. 启动恢复

应用启动时，在允许新的正式入库前检查所有未完成 `IngestOperation`。恢复器只能使用操作 ID、受控路径、大小、哈希、数据库版本和提交快照作出判断。

| 已观察状态 | 自动动作 |
| --- | --- |
| 暂存有效，尚未建立备份 | 继续既有操作 |
| 备份有效，目标不存在，暂存与意图完整 | 继续提交新文件 |
| 备份有效，目标不存在，输入或暂存无效 | 恢复旧目标 |
| 目标为新哈希，数据库仍是旧版本，证据完整 | 使用持久化资料快照完成数据库事务 |
| 目标与数据库均为新版本 | 进入或继续清理 |
| 目标和数据库均已恢复为旧版本 | 清理本次临时产物 |
| 目标、备份、哈希或数据库版本互相矛盾 | 进入 `RecoveryBlocked`，不再修改 |

恢复动作必须幂等；应用重复启动不得重复创建资产、重复应用资料关系或覆盖不同内容。

`RecoveryBlocked` 不建立独立页面。对应项目右侧详情栏显示：

- 当前恢复阶段。
- 停止自动恢复的原因。
- “重新检查”。
- “打开文件位置”。

其他项目仍可浏览和处理；被阻塞的项目不能再次开始入库。

## 10. 延迟清理

清理清单可以包含：

- 普通待入库源文件。
- MP4/M4A 等前置处理的全部来源。
- 前置处理输出。
- 暂存和提交临时文件。
- 已经不再需要的替换备份。

清理要求：

- 每个路径必须来自持久化的受控清单。
- 单个路径清理成功后立即持久化，重启后不重复推断。
- 清理失败不回滚已验证成功的正式入库。
- 项目保持 `CleanupPending`，但不阻塞其他项目。
- 后台退避为 30 秒、2 分钟、10 分钟、1 小时。
- 达到本轮上限后等待下次启动或用户点击“立即重试”。
- 手动重试只重试仍未清理的项目，不重新提交文件或数据库。

## 11. 持久化与迁移

Stage 4 至少需要以下持久化变化：

- 冲突案例表。
- 冲突匹配项表。
- 案例所选策略与替换目标。
- 入库操作的冲突、目标、备份和恢复字段。
- 旧资产及资料关系的恢复快照。
- 按路径记录的清理项和完成状态。
- 恢复阻塞原因。

内容哈希迁移要求：

- 移除资产内容哈希的全局唯一约束。
- 建立非唯一索引，继续支持快速重复检测。
- 查询必须返回全部匹配资产，而不是单条结果。
- 迁移前后的既有数据、资产 ID 和资料关系保持不变。
- 从 Stage 3 数据库直接升级的测试必须纳入自动化验证。

## 12. 桌面交互与刷新

- 冲突检测完成后立即刷新卡片和右侧详情栏状态。
- 冲突弹窗完全由案例 DTO 驱动。
- 决策开始后显示明确的当前阶段，不使用无限期“排队中”。
- 操作、恢复或清理状态变化通过现有通知链刷新当前选中项目。
- 对比弹窗关闭后，焦点返回当前项目，右侧显示“处理冲突”。
- 案例失效时提示“文件已变化，请重新确认”，不得继续使用旧弹窗数据。
- 清理失败时显示“入库完成，清理待重试”，避免误导用户认为正式入库失败。

## 13. 故障注入

故障注入只存在于测试替身或测试配置中，不提供生产 UI、环境变量后门或任意脚本入口。

覆盖点包括：

- 操作记录创建后。
- 暂存前后。
- 旧目标备份前后。
- 新目标提交前后。
- 数据库事务前后。
- 每一种来源、临时文件和备份清理时。

每个点分别模拟普通 I/O 异常和进程直接终止。重启后必须能够安全继续、恢复旧版本，或者明确进入 `RecoveryBlocked`。

## 14. 测试设计

### 14.1 领域测试

- 同名目标的默认选择规则。
- 案例失效与重复提交幂等性。
- 重名后缀选择和外部抢占推进。

- 单个、多个内容冲突和组合冲突。

- 输入、处理输出、目标或资产版本变化后的重新验证。
- 受控 DTO 不泄露任意文件访问能力。

### 14.3 基础设施集成测试

### 14.4 Desktop 测试

- 占位预览。
- 失效、恢复阻塞和清理待重试提示。

### 14.5 离线包冒烟测试

## 15. 验收标准

### 15.1 Stage 4A

1. 名称、内容和组合冲突均能显示稳定的对比弹窗。
2. 关闭弹窗后重启应用，冲突案例仍可继续处理。
3. 跳过不修改正式库且不删除来源。
4. 保留两者使用安全后缀，显示名称不受影响，相同哈希能够成为独立资产。
5. 替换已登记资产时保留资产 ID 和实际文件名，资料完整换成待入库快照。
6. 替换未登记文件前建立基础备份。
7. 多内容匹配项只替换用户明确选择的单个目标。
8. 外部文件变化使旧案例失效，不发生错误覆盖。
9. 4A 自动化测试、迁移测试和离线测试包冒烟测试通过。

### 15.2 Stage 4B

1. 每个故障注入点退出并重启后不丢失新旧文件。
2. 不重复创建资产，不重复应用资料关系，不产生无法识别的正式文件。
3. 能安全继续时自动继续；输入无效而旧备份有效时自动恢复；证据矛盾时停止在 `RecoveryBlocked`。
4. 来源和备份只在正式文件及数据库均验证成功后删除。
5. 文件被锁定时进入 `CleanupPending`，解锁并重试后完成清理。
6. 单个项目恢复或清理失败不阻塞其他项目。
7. 从 Stage 3 数据库升级、完整自动化测试和离线包冒烟测试通过。

## 16. 交付物

每个验收点提供：

- 对应提交上的完整自动化测试结果。
- Windows x64 离线原生窗口 ZIP。
- 人工验收清单。
- 包内产品版本和 Git 提交号。
- ZIP 的 SHA-256。
- 数据库迁移验证结果。

4A 交付功能验收包；4B 交付 Stage 4 最终测试包。两者均不联网下载运行时、媒体工具或依赖。

## 17. 实施顺序约束

1. 先迁移领域模型和数据库约束，再接入 Desktop 弹窗。
2. 先建立持久化案例和重新验证，再开放任何替换按钮。
3. 先让三种策略共用既有入库状态机，再扩充恢复状态。
4. 先完成恢复不变量和故障注入测试，再把 4B 标记为可验收。
5. 每个验收点分别执行代码审查、完整测试、离线发布和包级冒烟测试。

本规格没有遗留产品选择；实施中的命名细节可以调整，但不得改变已确认的用户行为、安全边界和验收标准。
